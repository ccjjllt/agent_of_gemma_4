# 官方评分与 129 个公共开发任务：从头分析

截至 2026-10-24（Asia/Shanghai），本轮重新下载官方材料，静态审阅全部 129 个公共开发任务的题面、参考补丁和验证补丁，不采用旧研究的成绩或观点作为前提。

**建议采用 8 类主修复机制。** 这个数字是为了区分 Agent 的实际工作策略而选定的研究粒度，不是官方给定题型，也不是从 129 题中能唯一推导的自然类别数。每题指定一个主机制用于统计；跨机制、规模、规格缺失和验收问题另外记录，不能强行消除重叠。

逐题依据：[task-catalog.md](task-catalog.md)；机器可读目录：[task-catalog.json](task-catalog.json)；评分实现复核：[scoring.md](scoring.md)。

## 官方究竟如何评分

正式分数是当前评测 split 中通过完整验收的任务比例：

`score = resolved 任务数 / 该 split 全部任务数`

每题只有通过与未通过，没有按通过测试条数、补丁相似度、修改行数或仓库权重给部分分。参考补丁只是一个可行实现，Agent 不需要生成与它逐字相同的 diff。整个任务最后留下的有效补丁必须能在干净环境中应用并通过验收。

[官方 Evaluation](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/evaluation) 及当天重新下载的 [官方 HARNESS_README](sources/HARNESS_README.md) 给出公式与预算。所有任务生成补丁的总预算为 12 小时，包含 sandbox setup，不包含 patch validation；可以自行配置每题预算。时间影响最终能交付多少有效修复，不直接作为连续扣分项。

当前公开实现分两阶段：Container A 让 Agent 修改代码并形成 diff；Container B 从同一原始 snapshot 重建，应用有效 Agent 补丁与官方 test_patch，再执行验收。A 中的临时依赖、运行进程或未体现在 diff 中的修改不会自动进入 B。测试文件和若干运行配置的修改会被剥离。

必须区分官方数据筛选说明和实际验证代码：公开验证器通常执行 **test_patch 涉及的整份测试文件**，同时核对必过节点，不保证每次都执行整个仓库测试。它要求 pytest 正常退出、JUnit 确有通过测试且无 failure/error。required 节点不能 skip；无关测试可 skip。公开 129 题全都没有 FAIL_TO_PASS/PASS_TO_PASS 字段，因此通常从 test_patch 抽取函数名作为 required fallback。完整分支及行号见 [评分复核](scoring.md)。

[官方 Data](https://www.kaggle.com/competitions/gemma-4-developer-agent/data) 将这 129 题定义为公共开发/训练数据。排行榜是另一套隐藏任务，官方写约 120 题、公榜/私榜约各半，来自私有仓库。不能把开发集解决率当公榜成绩，也不能用下面的类别占比假定隐藏分布。

## 八类主机制

| 主机制 | 题数 | 区分依据 | 代表任务 |
| --- | ---: | --- | --- |
| M1 局部规则与边界条件 | 23 | 修正既有路径的判定、默认值、常量或声明式输出规则；可能需要横向保持多个入口一致 | requests_6592、rich_3944、fastapi_13786 |
| M2 数据表示与转换 | 24 | 在字符串/字节、字段/别名、结构/Schema、富文本表示之间保持信息和语义 | requests_6589、fastapi_14371、rich_3061 |
| M3 参数、配置与元数据传播 | 16 | 贯通入口、包含/递归层及消费者，补齐传递、继承、合并和优先级 | fastapi_14978、fastapi_13713、rich_3518 |
| M4 状态、缓存与资源生命周期 | 15 | 处理操作顺序、对象共享、缓存等价关系或资源创建/退出时点 | requests_7328、fastapi_14099、httpx_3672 |
| M5 算法与结构不变量 | 12 | 保证扫描终止、图遍历覆盖/去环、坐标转换或宽度预算守恒 | rich_4006、rich_3521、fastapi_14266 |
| M6 类型反射与动态调用解析 | 17 | 解析注解、包装/partial、类/实例、命名空间以及实际同步/异步调用方式 | fastapi_5077、fastapi_14448、rich_3006 |
| M7 外部协议与依赖兼容 | 14 | 适配动态对象协议、继承分派、Python/第三方库的版本契约 | requests_7502、requests_6757、fastapi_14186 |
| M8 新能力与架构实现 | 8 | 建立新的执行/表示子系统，或改变架构组织方式并保持外围行为 | fastapi_15030、fastapi_15745、rich_3930 |
| 合计 | **129** | 每题一个主标签；重叠另记 | |

主要判据是“要把该任务做对，最关键的推理操作是什么”，而非文件数量或标题里的 fix/feature/docs/test。新接口不自动归 M8：`fastapi_15280` 虽标题说支持 app.vibe，参考行为仅是新增方法并抛特定异常，归 M1；`fastapi_14978` 增加 strict_content_type 的难点在既有链路的覆盖优先级，归 M3；SSE/frontend 才需要新增成套执行能力。

八类的边界并非完全客观。例如 `rich_3676` 新增异常 notes 字段，但只是将已存在的 __notes__ 经字段送入既有渲染链，本轮主审归 M3；`rich_3486` 还需要新增代码位置提取计算与范围渲染管线，归 M8、反射为次机制。`rich_3942` 是多处外观规则同步调整，没有被实际使用的新架构，本轮归 M1，规格不足另记。这些判据使后续重新标注时可以讨论具体分歧，而非随意移动类别。

### 为什么仓库主题不够用

同为 Unicode：`rich_3944` 只改未知码点的默认占宽（M1）；`rich_4006` 要保证前导/尾部 ZWJ 等输入下循环终止和索引覆盖（M5）；`rich_3930` 建立字素表示、版本数据和配套计算体系（M8）。三者的 Agent 策略和所需证据不同。

同为样式：`rich_3518` 是配置未传给自动创建的列（M3）；`rich_3061` 是 tab 展开后文本与样式跨度同步（M2）；`rich_2943` 是清除 meta/link 后没有失效派生 hash 缓存（M4）。

同一函数甚至可以要求相反修复：`requests_6644` 在历史 snapshot 中要求把开头多斜线折叠为单斜线，避免下游错误解析；`requests_7315` 则要求删除该折叠，保留 S3 签名路径。`requests_6757` 还把字符串的 UTF-8 长度处理限定为 urllib3 2.x。不能把训练目标简化成一套固定“修法”。

## 每题还必须保留的四个维度

1. **规模与耦合**：文件数、变更位置、入口数量，以及是否同步/异步两套实现。参考补丁中 91/129 题只涉及一个文件，60/129 题新增与删除合计不超过 10 行，但这不等于简单；`fastapi_15661` 单文件新增 216 行 CLI，`fastapi_13786` 则是相同错误契约跨 11 文件的一致修改。规模不作为机制分类阈值。
2. **规格充分性**：仅凭 Agent 当时可见的题面和 snapshot 能否确定预期。`fastapi_15280` 的愚人节异常、`rich_3942` 的具体颜色/对齐没有在题面自足说明；有外链的任务须记下外链，不能把未审读链接等同不存在线索。用参考补丁补全的事后规格不能伪装成题面显然可推导的信息。
3. **版本与协议条件**：修复必须针对各自 base_commit 和依赖语义。相反修法、Python 反射版本、Pydantic/Starlette/urllib3 兼容矩阵都在这一维体现。
4. **验收覆盖与可靠性**：需求、参考实现和评分 oracle 不是同一个集合。`rich_4070` 题面是导入性能，公开 test_patch 没有计时断言；`httpx_3672` 金补丁跨连接生命周期，但公开 test_patch 直接修改的是五个 parser 测试中的 complete→reset 调用，不能据此声称全部新行为都被直接断言。

另有明确的公开实现冲突：`rich_3486` 新增两个按 Python 3.11 互斥 skip 的测试，而当前公开 helper 在 fallback 下要求两者都 pass。一次性手动 AST/XML 复核重现了该分支冲突，**未执行真实任务或私有线上 scorer**。另一个静态冲突出现在 `fastapi_14186`：required 同时包含 Pydantic v1-only 与 v2-only 测试，在单一主版本环境中不能同时通过。精确 base_commit 的装饰器与 skip 别名已核对。另有20项依赖/平台/fixture条件候选和3项已排除误报，不能将这些候选直接算成无效任务。它们是 oracle 可靠性问题，不能直接当 Agent 能力差，也不能据此声称线上必挂。详见 [评分复核](scoring.md) 与 [逐题验收条件记录](oracle-caveats.json)。

## 这份分类怎样用于下一步研究

先把“任务需要什么机制”和“Agent 实际卡在哪里”分开。本轮得到的是前者；后者要在合法的开发运行中查看真实过程，再决定定位、推理、代码交付或环境处理的具体改进。静态主标签不能证明某种策略已经有效。

这些任务还有连续修补链：wraps/partial/class、字符串注解、Optional/Union、字段别名、路由包含树，以及 Requests 的斜线/编码兼容。训练与本地验证的划分应按相关修补链和 snapshot 家族保留隔离，避免同一历史演化的近邻进入两边后产生虚高。两对任务甚至共享同一 base snapshot：rich_3882/rich_3894、requests_6629/requests_6589。

下一步的优先事项是根据这八类组织独立开发材料，复核当前公开验证器中的环境/required 问题，再设计能观察真实修复收益的开发实验。此报告没有预先选择旧 Agent、旧权重或旧训练方案。
