# Prospective source-bytecode runtime policy — 未实施

当前官方SubprocessManager.exec构造的extra_env仅含VIRTUAL_ENV/PATH/PYTHONPATH，随后交给adk_eval_core.build_sanitized_env。后者只继承_SAFE_ENV_KEYS；其中没有PYTHONDONTWRITEBYTECODE/PYTHONPYCACHEPREFIX。因此collector host的这些环境变量不会自然进入task Python。实际纯函数观察也确认host flag1被丢弃，而显式extra_env能保留1。Manager构造器/exec没有直接env参数；不能假称已有配置传入生效。

可供root决定的最小新profile：collector使用显式版本化的manager环境适配层，把PYTHONDONTWRITEBYTECODE=1放入真正effective extra_env，覆盖phaseA/baseline/repaired的全部repository subprocess；在source复制后且任何预载/import前清除workspace包内生成的对应source bytecode。只针对生成缓存，保留原source/test/配置和只读依赖profile，不清测试用bytecode fixture或无源码模块。当前prepare_workspace本已排除__pycache__，但任务中默认Python又会写入缓存；只清初始化而继续允许写入仍会复现同秒同size问题。不要靠重设source mtime或sleep规避。

可在失败清理前有界记录实际改过的.py文件bytes/SHA/mtime_ns/size及其pycache16字节头，以免重演首轮证据被stop删除；这是故障证据，不是新准入门控。effective flag与初始cache policy应进runtime语义身份；不能仅比较整份带路径的runtime JSON哈希。此方案只处理新Python进程的timestamp+size命中；已经运行进程中的module对象/引用仍需显式reload或新进程，不由-B或清磁盘cache解决。

源码定位与实际SHA在prospective-runtime-policy.json：swegemma/sandbox/subprocess.py的exec/Popen调用与stop；adk_eval_core/sandbox/subprocess_sandbox.py的_SAFE_ENV_KEYS、builder和Popen；collector run_official.py的prepare_workspace/start/stop适配。全部只读，尚未修改这些文件。现有证据只说明本机SubprocessManager，不推出Docker/Kaggle等价。
