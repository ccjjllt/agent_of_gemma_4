# 四个 adapter 的能力分工与训练建议

2026-10-24。本方案依据129个公共开发任务的逐题机制目录，以及本轮重读的官方adapter规则。它是待验证的训练/路由方案，没有启动训练、GPU或真实路由实验。

**采用 G（通用）r128 + S（表示与算法）/F（流转与状态）/R（动态语义与兼容）各r32，训练计算与adapter导出均为BF16。G仅训练文本q/o和MLP五种投影，三位专家保留七种文本投影。** 原有八类用于机制分析，部署的四个adapter按能够共同学习、也能够用运行时证据识别的能力组织。

## 推荐的四个角色

| adapter | 重点能力 | 公共题画像 | 默认交给它的任务 |
| --- | --- | ---: | --- |
| G 通用仓库修复 | 规格恢复、代码定位、工具使用、增量实现、跨机制组合与最终交付 | 覆盖全部129题 | M1局部规则23 + M8新增/重构8 = 31题；以及路由不确定任务 |
| S 数据表示与结构算法 | 转换保真、编码/解析、别名/多值、字符与cell坐标、样式跨度、扫描与遍历不变量 | M2 24 + M5 12 = 36题 | 表示转换或结构算法是主要瓶颈 |
| F 跨层流转与状态生命周期 | 参数/配置/元数据传播、覆盖关系、共享引用、缓存、退出栈与异步资源 | M3 16 + M4 15 = 31题 | 执行链、配置流转或历史状态是主要瓶颈 |
| R Python动态语义与依赖兼容 | 注解与callable解包、globals、类/实例、动态代理、MRO、Python/依赖版本矩阵 | M6 17 + M7 14 = 31题 | 运行时对象或依赖契约是主要瓶颈 |

G的129题覆盖与三位专家重叠，不是四个互斥训练集合。若只是统计默认负责人，G/S/F/R分别为31/36/31/31，合计129。**这些数字是能力画像，不是已经选定、生成或足够训练的样本数。** G必须在全部机制上有基础能力，不能仅使用M1/M8的31题来训练“通用”。

逐题默认归属与额外专家关联见 [four-adapter-task-map.json](four-adapter-task-map.json)。该标签来自读过参考补丁的离线分析，线上路由不能访问这些金标签。

具体数据量、来源、机制证据和协议转换见 [训练数据准备方案](data-preparation-plan.md)：Verified Focal Agent RL首批96题已补齐逐题来源/机制，正在取得真实六工具成功过程；1,400题保留为后续扩展目标。来源供给、实际工具过程与已验证动作对分别记账。详见 [vfarl/README.md](vfarl/README.md)。

## 合并依据

S中的M2与M5共享明确的结构推理：字符数不等于字节数或显示cell数；变换后位置、跨度、顺序和信息必须一致。数据不能只按“Unicode/Markdown/URL”主题收集，应覆盖同一不变量在不同仓库中的实现。

F中的M3与M4共同要求沿执行/对象关系追踪影响：一个scope没有传到消费者，最后体现为资源退出时点错误；一个共享列表被兄弟分支修改，会体现为配置或权限污染。训练可以共同强化关系追踪、所有权和操作顺序。

R中的M6与M7共同要求恢复真实运行契约：声明类型不等于对象能力，wrapper不等于真正callable，类本身不等于其实例的__call__，版本名称也不等于相同编码/返回值语义。

M1按局部修复粒度收纳，M8含多种新增/重构工作；二者并非单一可迁移专科。让G承担这些任务，同时按具体证据调用专家，避免把多机制工程全压给一个样本少的“新功能专家”。

## 训练组织

1. **G与专家分别按最终结构初始化，使用共同的通用修复材料。** G直接初始化为r128、文本q/o+MLP五种投影。专家另外形成r32、七种文本投影的共同LoRA起点。合法、非预留评测的修复材料覆盖定位、输入输出契约、依据代码证据修改、必要的手动核对与patch交付；训练计算及adapter导出均采用BF16。
2. **仅三位专家复制同一r32起点，再分别继续训练S/F/R。** G保持广泛通用训练，不直接复制、补零扩容或截断专家权重。G与专家的rank和target范围不同，共享课程与数据原则不代表权重结构相同。最终每个分支各是一份完整adapter。
3. **专科提高采样占比，同时保留共同能力。** 可从70%专科、30%通用的监督token混合开始；这是起点，不是已证明最优比例。按独立任务数、仓库数和监督tokens分别记录，不把一题生成的多条轨迹当独立题。
4. **向其他合规仓库扩充同机制材料。** 129题的36/31/31个专科画像不足以证明能训练出可靠专家。优先保留这些公共题用于开发比较，训练材料另外扩展；不自动将预留比较题转成训练数据。若后续用户明确选择使用部分公共题训练，也先按修补链/snapshot家族划分用途并记下来源。
5. **监督必须对应实际证据。** 题面→参考patch只能提供部分实现监督；定位、环境处理和路由还需要带观察依据的真实修复过程，不能伪造执行成功或把验证补丁当Agent可见输入。

专家起点分化后，部署始终是G/S/F/R四个adapter目录；G独立采用其r128五投影结构，不额外提交或叠加第五个共同adapter。每次agent请求使用一个adapter；agent之间的顺序协作不等于把LoRA矩阵相加。各agent在声明式配置中选择各自adapter，并共享同一个官方31B base variant。

## 如何判断这种分工有用

比较的对象应是G单独修复与G+实际路由的专家系统，在相同任务和总时间预算下的真实resolved与耗时。按金标签选择专家的结果只可作为理想路由诊断，不能作为部署成绩。还要观察误路由、专家相对G的净修复收益和额外token/时间成本。

如果某位专家没有改善它接手任务的真实解决率，就保留G接手这些任务，不为了“四个adapter”维持没有收益的分工。类别覆盖并不能证明梯度一致、专家优于G，或路由已经可靠。

本轮不新建测试套件或门控脚本；后续研究仍按项目约定进行必要的手动验证和官方开发实验。

## 尺寸规划：G r128五投影，三位专家r32七投影，全部BF16

[官方规则](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/model-selection-budget-and-harness-rules) 与 [本地官方HARNESS_README](sources/HARNESS_README.md) 约束的是 **整个解包提交 <3GiB**，包括adapter、提示词、配置与skills。四个adapter本身没有数量障碍，所有agent仍需使用同一base variant。

用户已选择保留G=r128、三个专家=r32及BF16，将G范围收窄到文本q/o和MLP五种投影以满足预算：

| Adapter | Rank | 文本target_modules | BF16纯LoRA载荷估计 |
| --- | ---: | --- | ---: |
| G 通用仓库修复 | 128 | q_proj、o_proj、gate_proj、up_proj、down_proj（300个模块） | 1618.750MiB / 1.580811GiB |
| S 数据表示与结构算法 | 32 | q/k/v/o + gate/up/down（410个模块） | 467.031MiB / 0.456085GiB |
| F 跨层流转与状态生命周期 | 32 | q/k/v/o + gate/up/down（410个模块） | 467.031MiB / 0.456085GiB |
| R Python动态语义与依赖兼容 | 32 | q/k/v/o + gate/up/down（410个模块） | 467.031MiB / 0.456085GiB |
| **合计** | | | **3,166,535,680 bytes / 2.949066GiB** |

距离3GiB剩 **54,689,792 bytes = 52.15625MiB**。将safetensors头信息、所有配置、提示词和skills等非纯张量载荷合计按不超过32MiB规划，另留约20.156MiB余量；最终严格以全部解包文件实际字节数为准。不随提交携带optimizer、checkpoint副本或训练状态。

若G仍使用七种投影，r128+3×r32的BF16纯权重为3.192596GiB，会超限197.219MiB。本方案已按用户选择只去掉G的k_proj/v_proj LoRA；三个专家仍保留这些投影。G不使用k/v LoRA的能力影响尚未验证，不能将rank变大直接当作修复收益。

尺寸计算来自官方31B CT v2配置和Transformers文本attention构造：标准BF16 LoRA为 `2 × r × Σ(in_features+out_features)` bytes。全七投影S=7,651,840；G五投影S=6,630,400。范围限定在语言模型文本模块，排除vision/audio、embedding、lm_head、bias、modules_to_save、DoRA等额外参数，不是任意`all-linear`配置的体积保证。

已明确要求 **BF16训练计算与BF16 adapter导出**。训练计算dtype不会自动保证保存dtype；实际交付时核对safetensors张量为BF16。若导出成FP32，纯权重会翻倍为约5.898GiB，不能满足预算。官方比赛推理base仍使用允许的W4A16 variant。

尺寸依据见 [逐模块计算与所选配置](sources/four-adapter-size-calculation.json)、[官方CT配置副本](sources/31b-ct-v2-config.json)、[本轮官方规则快照](sources/official-adapter-rules-20261024.json)。这是配置/模块构造的解析估计，没有读取新的CT权重shape索引，也没有运行GPU/vLLM兼容实验；本次仅更新方案，没有训练或导出任何adapter。

## 四个纯专家的备选

若明确需要四个互斥专科，可以从A契约表示=M1+M2(47)、B动态兼容=M6+M7(31)、C流转状态=M3+M4(31)、D结构与实现=M5+M8(20)起步。但D把迭代算法和SSE/路由树等机制混合，解释力弱。

把SSE、路由树、RouteContext转入C，延迟导入转入B，得到47/32/34/16。D只剩16个公开画像，且仍混合新增CLI、frontend和字素算法。这个备选可研究，但不能依据数量均衡就认定优于G+S/F/R；当前推荐保留通用覆盖未知需求。
