# 当前 GRPO 方案

更新：2026-10-30。目标：用比赛129道公开任务训练独立 LoRA，挂载官方 W4A16 CT 基座。双A800已完成BF16基座与LoRA加载，并产生真实工具调用；完整题组、GRPO更新和CT效果仍待实测。

## 模型与更新

| 项目 | 配置 |
| --- | --- |
| 硬件 / 基座 | AutoDL A800 80GB × 2；对应 QAT 未量化31B，BF16冻结基座 |
| 训练后端 | Unsloth跨卡分层；TRL 1.15 `GRPOTrainer`负责裁剪目标、KL和优化器生命周期 |
| Adapter | r32 / alpha64 / dropout0；400个文本投影，暂排除共享K/V映射待验证的10个full层 `k_proj` |
| 上下文 | 每次实际模型调用总窗口32,768；保留完整任务轨迹、官方上下文管理和完整验收 |
| 采样 / 复用 | 每题8条完整轨迹，每批目标4题；同批最多更新2次，之后重新采样 |
| GRPO目标 | 概率比裁剪0.2/0.28，固定初始reference、KL系数0.01；固定长度归一 |
| 优势 | 各题组内中心化并按标准差归一，分母下限0.05，避免放大小幅效率奖励 |
| 数据 / 交付 | 服务器手动获取官方原始资产；导出独立PEFT adapter |

每次调用保存真实输入、生成token和行为概率。旧learner概率现在从第一次完整梯度前向的数值副本冻结，首次optimizer.step前完成整批冻结，复用期间不刷新；同一前向的带梯度结果用于真实TRL损失。reference一般单独评分，完全相同调用的已测固定reference概率可从有界CPU缓存复用；结构核对证明普通零LoRA与基座等价时，可共享首次梯度评分。没有截短历史或detach前缀KV。

第二次梯度前向同时计算整批生成token加权的旧策略漂移。KL超过0.05时丢弃该次整批梯度、停止剩余复用，优化器和学习率调度不推进；拒绝时已经发生的反向成本单独记录。两次更新都执行时，通常每调用从5次完整前向降至3次；零LoRA等价或reference缓存命中则为2次，不含checkpoint重算。仅生成token计损失，按真实前缀逐调用反向；行为与learner的概率差仍使用上限2的固定重要性权重修正。

上述复用改动已用真实TRL及极小Gemma4在CPU对照：4调用、两次更新由20次前向降至12或8，三批loss、LoRA参数和Adam/scheduler状态与旧实现逐值一致，前缀梯度非零。低KL阈值拒绝第二次更新时未改变第一次更新后的参数和优化器状态。数值记录在`results/local-grpo-reuse/2026-10-30/numerical_summary.json`；GPU时间收益未实测，详细边界见[轨迹复用说明](../training/README.md#轨迹复用中的前向合并)。

## 复合奖励

`R = 1×完整修复 + 0.3×FAIL_TO_PASS修复率 − 0.5×PASS_TO_PASS回归率 − 0.02×成功轨迹token成本`

分项来自同一次完整官方验收的JUnit报告，仅裁判侧读取测试信息；效率项在成功后计算且有上限，不提前截断轨迹。成功奖励始终高于失败最高分。组内任一候选缺少可靠分项证据时，全组停用测试分项，保留终局和成功效率奖励，避免缺失统计带来虚假优势。基础设施或无法归因的验收失败不伪装成零奖励。

## 动态采题与筛组

- 先覆盖未访题，再结合奖励方差、中等成功率和访问次数调整采样优先级；保留20%均匀探索，并降低同批重复仓库的优先级。
- 每组8条全部完成后才判断奖励方差；低于阈值的组保留真实结果并让新题补位。
- 每批最多尝试12组，不反复重采同一题；不足4个有效组时按实际组数更新，没有有效组则不更新。
- 记录实际选题概率、全部候选与入选组的成功率。自适应采样和筛组改变了训练分布，不把入选组成绩当成129题均匀评估成绩。

## 执行边界与入口

题面、`base_commit`和官方资产保持原样，参考补丁与验收资产仅供裁判侧；排除列表中的题不进入采样器。工具与验收使用独立CPU进程及低权限UID。10月30日已将生成入口改为逐步连续批处理、同策略版本的有界前缀KV复用和跨题组有界预取；这是新代码状态，下面的`first-batch-008`仍是此前串行版本的实测记录。

首批先取1个有效题组、每题仍采8条完整轨迹，最多尝试3题；同批最多更新2次，总进程上限2小时。正式配置仍为每批4组、最多32批。会话预算显式设为60分钟、100次工具调用、50回合，命令与验收超时各300秒；原版示例的1分钟/10次工具预算仅在运行配置中覆盖。

`first-batch-008` 于北京时间01:21:20启动，首题为 `fastapi_15023`。已取回的01:29:50日志快照记录11次完成调用、1297个输出tokens、410.75秒生成时间，合计3.16 tokens/s；首次logits返回前计时合计27.12秒（6.6%），最长GPU排队184.78秒。加载约30GiB/卡，生成约33GiB/卡。尚无完整题组、奖励或GRPO更新的证据。

主机最后确认在线时间为01:27:34，01:30之后SSH持续拒绝连接，关机状态尚待确认。14份主日志、运行配置及依赖记录已取回本地 `results/autodl/`（共133962字节）；最新主日志停在第12次调用生成128 tokens的进度，不能当作最终结束日志。未取回官方题目、原始轨迹token、补丁或验收资产。

当前证据指向解码开销和GPU串行队列；原CPU线程池已经会在轨迹完成时立即补位。新调度让活动序列共用decode forward，并在步间接纳新请求；题组之间也能有界重叠，完整组仍按选题顺序决定是否训练。前缀缓存只作为补充，不把它当成解决主要解码瓶颈的依据。

实现沿用原生逐层`DynamicCache`，没有直接打开Transformers5.17的paged连续批处理：该版本[缓存分配源码](https://github.com/huggingface/transformers/blob/v5.17.0/src/transformers/generation/continuous_batching/cache.py)采用统一KV头形状，与Gemma4异构full/sliding层不符。当前保留跨卡分层，未实现张量并行；长prefill仍逐个处理。详细配置与限制见[生成调度说明](../training/README.md#生成调度与性能测量)。

必要手动核对已用极小随机Gemma4在CPU完成：批内异长前缀、滑窗跨界及共享KV与独立完整前缀forward一致到浮点误差；实际连续采样19个token的behavior logprob最大绝对差约2.4e-6，最大活动batch为3，覆盖中途加入和退出。HTTP调度、取消与完整题组选入顺序也已核对，未新增测试文件。CPU数值记录在`results/local-batching/2026-10-30/`，不能用CPU吞吐声称31B加速。
