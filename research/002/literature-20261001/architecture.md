# 五分钟 Gemma 4 修复：Agent 架构、上下文与编辑接口证据备忘

检索日期：2026-10-01。只读文献与作者代码；没有安装、模型运行或实验实现。本文负责架构机制，不重复环境门槛；提出的接口和实验均交用户后续实现。

## 研究判断

建议把下一轮算法创新集中到 **分层提供代码证据 → 尽早产生有效源码编辑 → 保留少量可恢复状态**。不是继续给同一长轨迹加“别循环”的指令，也不是增加全仓图展开。优先做一个具有明确机制的技能增量：**按文件/类/函数层次查找并返回完整的相关结构，读取结果直接产生后续编辑句柄**。

本项目已知：P003 的行为提示没有面板净增；P002 降低输出预留消除了一个上下文异常方向，却未增加解决数，按冻结规则保留16384。它们共同支持研究“交给模型的信息和动作是否合适”，尚不能证明模型本身无法修复。现有 T1 提供符号查找、分段读取与提交前报告，但还没有层级概览、带快照身份的编辑接口、压缩后的明确交接。

本文选5项：Agentless 的2024公开论文版本及2025发表资料、mini-SWE-agent作者项目、2026 SWE-Pruner，以及作为必要机制对照的2024 AutoCodeRover和SWE-agent。后两者不是“2026前沿”；保留它们是因为有可对照的定位/接口机制。未用社区分数、商业宣传或二手摘要作结论。

## 2. 五项研究真正有用的信息

### A. Agentless：文件骨架比整份文件更适合决定“下一步看哪里”

公开v2 Table2中，类/函数定位使用骨架比完整文件保留更多gold位置（58.33%对53.67%），且上下文更少。骨架保留定义结构，先选文件，再选符号，再给局部代码。Table3最优32%同时使用40补丁，不能将总分全部归因定位。Contains-GT只是事后指标，不是给Agent的答案；42%候选并集也不是实际选出补丁的分数。[论文§3、§4、Table2–3](https://arxiv.org/html/2407.01489v2)

**本项目推论**：现有find_symbol偏向“已有名字找命中”。遇到issue只有行为描述或同名歧义，应补`outline`：先给有限目录/文件概览，再给类的签名与成员，再展开少量完整函数。当前简单截取前400字符可能把关键分支切掉；分层压缩比更短的字符截断更有研究价值。

不采纳原样40候选、40测试、多模型embedding和全量回归筛选；它们主要是推理计算扩展。首轮只比较上下文组织方法，保持一次主要修复路线。

### B. AutoCodeRover：一次查多个有依据的符号，逐步收缩范围

其API以类、方法、文件为约束；类搜索只给签名，方法搜索给实现。关键词来自issue，随后新符号来自已读代码。基础组无gold位置输入；论文19%→22%的SBFL实验则额外获得开发者新增测试及top5可疑方法，信息条件不同。约4分钟是GPT API环境统计，不是本地31B的速度承诺。[论文§4.2–4.3、§5、§6.2](https://arxiv.org/html/2404.05427v3)

**本项目推论**：应允许一个技能调用携带少量`queries=[...]`，将同一次决策的2–4个相关符号一起查询，按“明确路径→类→方法→引用候选”返回。这样可减少多个短工具调用之间的模型往返。批量不是无界扫描，结果仍共享总输出预算；不能一次塞回所有候选正文。

这不需要先接图，也不需要先加子Agent。阶段分工可先在单Agent内通过不同技能动作实现；只有长探索历史干扰编辑得到支持后，再测串行定位者→修复者。

### C. SWE-agent：编辑接口本身比“请准确编辑”更值得研究

同一GPT-4设置下，Lite的完整接口18.0%，去掉编辑器10.3%；完整文件阅读12.7%，100行窗18.0%；逐条翻搜索命中12.0%，汇总式18.0%。这些是其论文条件下的消融，非本项目预期增益。编辑后立刻给更新窗口，错误在当次动作返回，减少无声失败。[论文Table3与§5.1](https://arxiv.org/html/2405.15793v3)

**本项目推论**：T1目前仍让模型重新输出整段old_string。可以让读取技能返回`span_id`，在本题临时状态中绑定路径、原文、行范围、文件/区间哈希；编辑技能只接`span_id + replacement`。它校验当前源码未变，再原子替换并返回最小diff与新片段。这样不是猜测性模糊匹配，也无需模型重复抄写旧代码。

研究收益点是减少编码旧文本、转义和定位歧义耗费的生成时间；不是再次建设通用测试系统。原文不匹配时一次明确反馈，避免连续相同FileEditError。新源码仍由Gemma生成，技能不包含答案。

### D. mini-SWE-agent：简化是需要保留的反假说

作者路线强调仅bash、每条命令独立执行、线性消息历史；作者明确把这种简化与较强新模型联系起来。它不证明所有模型都不需要专用接口。当前repo页面没有一组能同时对应本项目模型、上下文和5分钟预算的成绩，故不移植首页分数。[作者repo](https://github.com/SWE-agent/mini-swe-agent)、[作者FAQ](https://mini-swe-agent.com/latest/faq/)

**本项目推论**：技能API宜少而稳定，避免让Gemma先选择十几个重叠工具。建议只保留3种认知动作：`locate`、`inspect`、`apply`（提交/验证仍沿官方工具）；实现可以共享一个技能入口的mode。若同一定位能力用普通命令也能一次完成，不能仅因接口更复杂便预设其有益。

这里不是建议重写Harness成为mini，也不是建议清空必要历史；只将“额外架构可能成为决策负担”作为选择机制时的约束。

### E. SWE-Pruner：裁剪目标应来自“当前要判断什么”

模型按Agent给出的goal hint对代码行保留/删除。论文Table1的Verified结果是Claude70.6→72.0、GLM55.4→56.6；平均token降低23.1%/38.3%。其0.6B筛选器和250轮上限与本项目不同。正文/附录另有不同节省百分比，本文仅采用Table1，不混算。[论文§3.4、Table1、AppendixD.2](https://arxiv.org/html/2601.16746v3)

**本项目推论**：不提交额外skimmer。借用目标条件化思想，让inspect参数表达“要确认的符号/分支/异常字符串”，以标准库AST与文本匹配提取完整语法单元：相关函数体保留，旁支先只给签名。明确标注省略，并能用句柄恢复原文。不要把经过删行的片段当可直接编辑源码。

该方法与把全文总结成自然语言不同：保留真实代码和稳定位置，对精确编辑更友好。是否比当前窗口读取更好仍是本项目假说，尤其要防止省略了真正根因。

## 3. 可提交机制与项目自身推论的界线

| 机制 | 通过现有提交形式落地 | 限制 |
|---|---|---|
| 分层outline、受限批量符号查询 | Python skill，经官方run_skill_script | 不需额外模型；同一issue/本题源码构建，不能引用gold/其他运行轨迹 |
| 目标导向的完整函数/分支片段 | Python skill参数与结构化输出 | 是SWE-Pruner思想的确定性近似，不是其训练模型或论文方法复现 |
| span_id/源哈希绑定的编辑 | Python skill，在本题临时状态保存已读原文 | 不是修改host edit_file；仅在技能被调用时生效，不自动拦截其他编辑方式 |
| 本题外部状态卡 | skill保存事实；原生read_file/run_command可取回 | 本文新设计推论，没有引用论文证明对Gemma4有效；不会自动删掉ADK旧上下文 |
| 串行locator→coder | SequentialAgent/output_key/include_contents | 所有阶段共用5分钟；没有已证每个子Agent独立硬时间配额 |
| SWE-agent的last5历史处理器 | 不能直接通过当前YAML替换host history | 可用明确交接/新子Agent上下文近似，但不是等价复现 |
| SWE-Pruner额外0.6B模型/内部剪枝头 | 当前比赛提交不能原样采用 | 只允许指定基座；隐藏状态hook也没有声明式入口 |

外部状态卡建议只保留：问题目标一句、已确认源码句柄、关键调用关系、当前假设及反例、最后一次有效diff和下一个动作。技能可自动追加机械事实（文件哈希、命令结果、编辑成功/失败），语义假设由Gemma写短句；不记录冗长思考。单Agent阶段只是避免反复读取，只有后续串行交接才研究是否减少历史干扰。

## 4. 建议给用户实现的三个具体实验假说

### H1：分层结构 + 同决策批量查询，能更早得到可编辑上下文

**优先级1；本次最明确的定位研究方向。** 与现有T1相同模型/预算/其余编辑方式，仅将find_symbol/read_range组织扩为outline→少量有约束查询→目标函数。示例输出先是3个候选文件及相关类签名，再由Agent选1–2个函数体；不再用前400字符代表函数。

预测：达到首次有依据的有效源码编辑所需LLM往返减少；相同5分钟内更多任务拥有生产修改且最终解决。解释指标是查询/阅读累计输出、同文件重复读取和编辑前轮数，不把token下降单独当成功。若省略关键证据导致回读增多，应调整结构保留方式，而非再加“更专注”的指令。

### H2：读取句柄直接用于编辑，能减少机械性编辑失败

**优先级1，与H1分开比较。** 保持相同上下文和定位策略，只换“复制old_string→span_id+replacement”。完整函数较短时可做函数级替换；长函数用哈希绑定区间。返回编辑前后少量行和小diff，不默默改动整个文件。

预测：FileEditError链、模型输出旧代码的token、第一次成功编辑耗时下降；尤其适用于P003/P002已经读到目标区域却迟迟编辑失败的案例。若失败来自修复逻辑，句柄接口不会提高正确率，应如实区分。先不引入多候选补丁或新增自测策略，避免无法解释改善来源。

### H3：一次明确交接，能摆脱探索历史对修复阶段的干扰

**优先级2，待H1/H2能形成紧凑证据包后。** 单Agent与串行locator→coder比较，双方可用相同检索/编辑技能。定位者只输出候选位置、关键证据及一个可检验修复假设；coder接收issue+该输出，可继续查证。locator不具有submit_patch，避免提前截断整题。

这是上下文隔离实验，不是更多算力：同一Gemma、总5分钟、同工具总额；定位者的软轮次目标应短，不能宣称硬隔离保证收尾。只有一次交接，不上协调者/复核者/多轮辩论。预测长探索失败题获益；风险是交接丢掉反例、重复定位及角色切换成本。

一个更便宜的前导变体是仍用单Agent，只增加可取回的状态卡；它不减少ADK现有历史，因此不要把状态卡收益和“上下文重置”混为同一机制。

## 5. 暂不作为主线

- 多候选补丁投票：Agentless表明它可能提高覆盖，但40补丁/40测试及排序不符合当前5分钟；以后至多研究小规模备用假设，不能原样移植。
- 用官方图邻居替代层级源码证据：本项目索引存在快照对齐与区分度疑问，本文文献也没有证明图普遍胜过结构化源码检索。
- 额外神经检索器/压缩器：许多2025–2026工作依赖另一模型或hidden-state接口；当前应迁移信息组织机制，不扩展到不具提交入口的服务。
- 将“便宜/快/低token”直接当比赛收益：API美元预算、云端强模型平均时长均不等于本地Gemma五分钟有效动作数。
- 立即上完整多Agent系统：mini提供相反方向的实践；先用同样能力证明单次交接有益，再增加架构。

## 6. 证据边界

本文没有声称某一论文能保证本项目提高若干百分点。所有假说都固定本项目基座与总预算；使用issue/允许hints/本题工作区，不使用参考修复、终局隐藏测试输出或其他组轨迹。文献的gold位置命中率只解释论文结果，不成为本项目运行输入。

仅阅读5项的原文和作者实现；未把SWE-Pruner预印本写成已获顶会录用，未把2024工作包装成新论文。来源定位与版本记录见[architecture-sources.json](architecture-sources.json)。

额外筛选但不扩展主名单：[ACL2026 Taming System Complexity](https://aclanthology.org/2026.acl-long.862/)实际研究Linux内核故障定位，非Python仓库端到端修复；[SWE-Pruner Pro](https://arxiv.org/abs/2607.18213)是2026年7月预印本，裁剪头直接读取coder内部表示，当前提交形式缺该入口。两者本次仅筛选摘要，不据此报告可迁移分数。
