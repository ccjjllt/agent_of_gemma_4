## 二、把 Agent 改成“修复 → 完工复核”两阶段架构

新主候选使用同一个 **31B 基座**（`gemma-4-31b-it-qat-w4a16-ct`，保持 8 分钟 / 28 次工具调用 / 80 turns 总预算，`temperature=0.2, top_p=0.95`），精简为职责明确的两个阶段：

```text
原始问题 ──► [阶段 1：修复阶段 (Repair)] ──(必要证据 + 当前工作树)──► [阶段 2：完工复核阶段 (Review & Submit)]
```

### 2.1 两阶段职责与上下文传递

1. **修复阶段（Stage 1 — Repair）：**
   - **核心职责：** 自主定位、读取目标源码与调用方/测试契约，尽早完成完整生产修改（含相邻分支与边界条件），运行有限的针对性验证（带 5–15 秒短超时与 `/workspace` 源码路径核验），最后输出实际修改证据、验证输出摘要及未完成项。
   - **工具配置：** 持有五工具（`run_command`、`read_file`、`edit_file`、`write_file`、`get_status`），**不持有 `submit_patch`**，避免未复核或半成品提前终止整题运行。
   - **交接输出：** 通过 `output_key: repair_handoff` 输出精简交接摘要（修改文件路径、核心逻辑变更、已执行的验证命令与退出码/关键输出、仍存疑或未覆盖的边界项）。
2. **完工复核阶段（Stage 2 — Review & Submit）：**
   - **核心职责：** 直接读取**原始问题全文**与当前工作树**真实 `git diff` / `git status`**；核对需求中的函数/类名、异常类型、报错文案、返回值与边界条件是否完整落地；检查是否存在本轮遗留的临时产物（`.tmp`、`repro*.py`、额外目录等）并彻底清理；若发现具体未完成分支、明显缺陷或空补丁，做**一次针对性纠正与短验证**，最后调用 `submit_patch` 完成提交。
   - **工具配置：** 持有完整六工具（含 `submit_patch`）。
   - **上下文隔离：** 设置 `include_contents: none`，直接从模板变量接收原始问题与 `{repair_handoff}`，不继承第一阶段冗长的搜索与试错历史。

### 2.2 编排实现与单 Agent 保底机制

- **官方 `SequentialAgent` 编排：** 复用官方 [`adk_submission/builders/workflows.py`](../../research/006/official-data-20261013/wheels-source/adk_submission/builders/workflows.py) 中的 `SequentialAgent`（参考 [`research/005/candidates/one_handoff/agent/agent.yaml`](../../research/005/candidates/one_handoff/agent/agent.yaml) 结构），由根 `agent.yaml` 固定顺序执行 `repair_agent.yaml` → `review_agent.yaml`，**无须额外增加一个负责调度的协调器 LLM**，省去 P012 中协调器来回转发消耗的 turns 与延迟。
- **阶段预算风险与单 Agent 兜底判据：** 官方 `SequentialAgent` 只固定执行顺序，**不提供单阶段硬性时间或调用次数上限**（整题共享 8 分钟 / 28 次工具调用）。因此：
  - 在第一阶段提示词中明确设定调用预算软上限（例如：第 1–6 次调用完成定位与读取，第 7–12 次调用完成完整生产修改，第 13–18 次调用完成短超时验证并立即停止工具调用、输出交接摘要，为第二阶段预留约 6–10 次调用与至少 90 秒预算）。
  - **实测检验与回退规则：** 第一阶段能否及时结束并交接，必须通过第四节“第一步：少量旧题诊断”的真实 31B 运行确认。**若实测发现第一阶段仍频繁耗尽 28 次调用或 8 分钟预算导致第二阶段沦为空壳，优先采用包含完全相同四项执行改进（P0–P1）的单 Agent 31B 版本**，绝不为了形式上保留两阶段而损失实际修复时间。

## 三、后训练同步推进：交付第一轮真正的行为 SFT

### 3.1 立即修正现有数据生产器的两项核心问题

核查 [`research/012/training-data/dataset-manifest.json`](../../research/012/training-data/dataset-manifest.json) 与 [`research/012/training-data/produce_p012.py`](../../research/012/training-data/produce_p012.py) 确认：
1. 当前 P012 的 256 条训练样本（`p012_repair_local_edit`）全部为 `behavior_verified: false`、`task_resolved: null` 的局部静态编辑回放，**0 条经过真实行为验证或错误恢复**。
2. `produce_p012.py` 第 277–289 行在构造被监督的尾部 assistant 交接消息（`handover`）时，硬编码写入了 `'requirement_done': True` 与 `'needs_other_route': False`，导致模型在**完全没有运行任何行为验证命令**的情况下被监督学习“报告需求已完成”。

**修正措施（P013 数据线第一步）：**
- 立即更新生产器协议与监督标签：凡未执行真实行为验证（`behavior_verified: false`）的局部编辑样本，严禁输出 `'requirement_done': True` 或任何“验证通过/已完成”表述；其尾部状态必须如实标记为“仅完成局部代码修改，尚未执行行为验证（`verification_status: not_run`）”，或仅监督其中的有效代码编辑动作（`edit_file`），不监督虚假交接结论。
- 严格区分**完整行为数据（主监督层）**与**旧局部编辑数据（辅助层）**：单独统计并控制完整行为数据在每个训练 epoch 中的采样占比与有效监督 token 权重，防止大量静态局部补丁淹没行为验证与错误恢复信号。

### 3.2 本轮真实行为轨迹生产目标与时间表

本轮训练的核心目标是让模型在真实工作区交互中学习完整闭环：

> **读取代码 → 修前失败 → 完整修改 → 根据真实报错纠正 → 同一判据通过 → 准确交接或结束。**

具体执行安排：

1. **分阶段产量目标（不等待 512 题）：**
   - **前 12 小时：** 集中完成**至少 32 个不同训练问题**的真实行为轨迹（含修前复现失败 → 生产修改 → 真实报错恢复/修正 → 同一判据通过）。
   - **24 小时内：** 向 **64 条真实行为轨迹**推进。
   - **优先复用已有资产：** 优先从已打通环境与验证命令的训练仓库（如 P009 已验证的 `apispec`、`marshmallow`、`pydantic`、`tenacity`、`mypy`、`deepdiff`、`yamllint`、`dataset` 及 P011/P012 71 个训练仓中的纯 Python/轻量依赖仓，见 [`train-repos-71.json`](../../research/012/evaluation/train-repos-71.json)）中提取并重放。
2. **真实性铁律（严禁造假与污染）：**
   - **验证真实源码：** 每条轨迹中的验证命令必须导入当前工作区修改后的源码（显式校验或设置 `PYTHONPATH`），修前必须观察到具体失败，修后必须在同一判据下观察到通过。
   - **真实错误与恢复：** 锚点匹配失败、API 参数误用、部分分支遗漏或修复后引发邻接报错及随后的修正过程**必须在真实工具执行中发生**；严禁为了凑错误类别而故意注入人工拼写错误、拼接其他题目的报错输出或伪造工具回包。
   - **未验证不标完成：** 若某题仅完成局部修改或验证命令受环境限制未能跑通，绝不标记为完成，也不计入 32–64 条行为配额。
   - **严格数据隔离：** 开发题（公共 12 题、外部 8 选择仓 `gpxpy/feedparser/pandas/schema/cookiecutter/conan/modin/iniconfig`、原 28 题 heldout、旧预留 8 题）中的失败**仅用于总结上述四类通用缺陷**；其问题正文、专用补丁、测试与答案严禁进入训练集。所有训练样本必须 100% 来自已冻结的训练划分。
3. **协议对齐与 SFT 启动节奏：**
   - 行为轨迹使用本轮最终选定的工具集与交接/结束协议进行编码（沿用 `gemma_tool_chat.py` 零基 assistant 序号校验，`--thinking on --thought-loss mask`）。
   - **首批 32+ 条合格行为数据形成后立即启动第一轮连续 SFT**，不等待凑齐 512 题。
   - 首轮继续复用已跑通的 **12B QAT/NF4 缓存 + 4×L4 DDP** 训练链路（`r=8, alpha=16, global_batch=4, lr=2e-5`，新建 LoRA 与 optimizer，不直接 `--resume` 旧协议 checkpoint）。
   - **双线协同与迁移路径：** 31B 的提交候选优化与 12B 的真实行为 SFT 同步推进；待 12B 行为 SFT 在同预算任务对照中展现出明确的修复收益后，再扩大行为数据规模并评估向 31B 迁移。

## 四、用更有效的实验决定提交

摒弃 P012 中多变量交叉的大矩阵（不再同时排列组合温度、checkpoint、多角色路由），改用“旧题机制验证 → 新题单候选配对确认 → 明确净增门槛决策”的三步法：

### 4.1 第一步：少量旧题诊断（确认机制真实发生）

选取已暴露代表性失败模式的历史诊断题（例如死循环卡 240s 的 `rich_4006`、首次编辑过晚且带临时文件的 `rich_3180`、导入系统旧包的 `requests_7205`、连交空补丁的 `requests_6757`），利用已有补丁、trace 与测试输出做小规模快速验证，逐项核实：
- 短超时（5–15s）是否成功截断死循环且未触发误撤回；
- 验证命令是否确切加载了 `/workspace` 下的真实修改源码；
- 首次生产修改是否显著提前（在 Call 12 前完成主体与关联分支修改）；
- 两阶段 `SequentialAgent` 的第一阶段是否按时交接给第二阶段，或是否需要切换为包含相同改进的单 Agent 版本；
- 最终补丁是否干净无残留临时文件、无空补丁重复提交。

> **边界约束：** 诊断阶段人工修好的补丁或环境修复仅用于验证机制与裁判区分度，**绝不计入模型修复成功数，也不作为提交依据**。

### 4.2 第二步：冻结单一新候选，在 12 道新开发题上做 31B 同预算对照

通过第一步确认机制生效并定型架构（两阶段 `SequentialAgent` 或同改进单 Agent）后，**立即冻结一个新 31B 候选包**，在 **12 个未参与本轮提示/代码修改的新开发问题**（覆盖多个训练外仓库，预先验证修前失败/参考补丁通过的裁判区分性）上，与**当前正式 31B 基线（`public022_v10`，0.15 方案）**进行完全同预算（8 分钟 / 28 次工具调用）的 1v1 配对评测（12 题 × 2 臂 = 24 attempts）。

**每题必须详细记录并对比以下四项核心指标：**
1. **逐题胜负与回退（Wins vs. Regressions）：** 新增修好哪些具体问题、分布在哪些仓库/问题类型；基线原本修好的问题有哪些发生回退及具体原因。
2. **首次生产修改时机：** 对比两臂首次调用 `edit_file`/`write_file` 修改生产源码的调用序号（Call #）与墙钟秒数，确认是否消除“拖到 400 秒后才改代码”的现象。
3. **异常损耗削减情况：** 统计单命令阻塞超时次数、空补丁（`patch_size=0`）提交次数、仅含复现脚本/只补 `import` 的半成品次数，以及最终补丁混入临时文件的次数。
4. **验证后行为回退检查：** 核查通过已有相关测试或内联验证后，是否在收尾阶段因过度修改或误删导致邻接行为回退。

### 4.3 第三步：正式提交决策规则（以“12 题净增 ≥ 2 题且跨类型/跨仓”为研发目标）

本轮设定明确的开发检验标准：**在 12 道新开发题对照中争取净增至少 2 题（`Wins - Regressions ≥ +2`），且新增收益覆盖不止一个问题类型或仓库**（注：此为内部研发验收目标，不换算或承诺公榜具体涨幅）。

| 12 题配对对照结果 | 决策与后续动作 |
| :--- | :--- |
| **达标（跨题/跨仓净增 ≥ 2 题，运行可靠，无明显回退）** | 立即冻结该 31B 新候选 ZIP（完成官方 `compile_submission` 校验与补丁卫生核对），执行正式 Kaggle 提交并跟进官方回执评分 |
| **临界（仅净胜 1 题，或虽有新增但伴随回退/证据混杂）** | 不直接盲目提交，也不全盘推翻；**只补一次小批新开发题确认**，核实净胜是否稳定 |
| **未达标（同分 `0` 或净回退 `< 0`）** | 深入拆解具体失败与回退轨迹，**针对具体根因修正一次**并复测；严禁通过不断扩大实验矩阵、枚举提示词变体或更换随机 seed 来寻找偶然漂亮结果 |
