# 003：上下文使用与时间预算

## 研究背景

本轮承接 [001：无 LoRA 基线](001-baseline.md)，使用其运行轨迹研究时间和上下文的分配。
按当前已核实的比赛说明，全部任务生成补丁共享 12 小时，其中包含沙箱准备时间。
因此，单题可以无限搜索或反复修改的策略不适合直接作为比赛策略。
研究目标是在明确的总资源约束下，提高完成有效修复的机会，并识别时间消耗的来源。
主办方 2026-09-24 确认隐藏任务顺序执行；当时触及 12 小时会使整次提交报错，计划修复不等于已经修复。
资料核对日期为 2026-09-28，后续预算与压缩配置变化应随运行记录保存。

## 研究问题与假设

- 限定源码读取范围和工具输出长度，可能减少无关上下文，但过度截断可能隐藏关键线索。
- 保存已确认事实与当前假设，可能减少重复阅读；效果取决于模型是否能准确利用摘要。
- 对长期无进展的任务设置停止条件，可能让更多任务获得处理时间。
- 分阶段预算可能优于统一的单题上限，但阶段划分和阈值应由基线测量决定。
- 以上均是待验证假设；本轮不预先认定某个时间上限或上下文长度最优。

## 前序输入

- 001 的可运行基线、按 `(repo, base_commit)` 分组划分的固定任务清单、指定模型与原始运行记录。
- 每题可取得的开始结束时间、工具调用、模型调用和运行错误。
- 官方 Harness 关于总预算、超时、任务顺序、并行及补丁提取的实际说明。
- 若采用 002 的定位策略，应固定为同一个版本，并记录选用依据。
- M5 32GB 用于资料整理和轨迹分析；GPU 配置以 Kaggle 实际分配为准。

## 先整理时间消耗

人工从现有记录区分环境准备、模型等待、代码定位、源码阅读、修改和任务结束等阶段。
阶段名称是研究分析标签，不是预设的官方事件或回调名称。
已有日志无法精确区分的时间应标为未知或合并记录，不能用估计填成实测值。
同时记录重复读取、连续相同错误、无补丁退出和补丁已生成后继续消耗时间的情况。
官方 README 明确单题 `max_time_minutes` 从 Agent 开始运行计时，不包含准备时间；总 12 小时包含准备时间。
据此分别记录准备与 Agent 耗时，不能以单题时限乘以任务数作为整次运行的完整时间估计。

## 已核实的配置与工具边界

提交根目录的 `eval_config.yaml` 在 `evaluation:` 下支持四个字段，主办方已确认评分器只读取这四个字段：
`timeout_seconds` 限制单次命令，`max_tool_calls` 限制工具调用次数，`max_time_minutes` 限制单题 Agent 时间，`max_turns` 限制推理轮数。
README 的具体默认值与主办方 9 月 24 日“默认无限制”的说法不一致，故四项全部显式填写，不依赖默认值。
`get_status()` 返回 `time_seconds_remaining`、`agent_elapsed_seconds`、`tool_calls_remaining`、`patch_submitted` 等当前状态，不消耗工具次数。
`submit_patch()` 不消耗工具次数，但要求尚有会话时间，策略应尽量在时限前主动收尾。
README 第 8.1 节明确：未调用 `submit_patch()` 而正常结束、达到提醒上限、耗尽工具/轮数或普通单题超时后，Harness 会在拆除沙箱前自动提取现有 diff；非空补丁仍进入后续验证。
该正常收尾机制不等于进程强杀或全局 12 小时中断后的恢复保证，后两者不能直接套用上述结论。
官方上下文窗口为 32,768 tokens；命令输出默认上限 5,000 字符，`read_file` 默认同时限制 150 行和 10,000 字符。

## 需要实现的改动：上下文部分

1. 在 001 的提示词中明确：先定位候选位置，再按函数或局部范围读取，必要时扩大范围。
2. 使用 `read_file(filepath, start_line, end_line)`，范围为从 1 开始且包含两端；遇到 `is_truncated` 继续按需分段读取。
3. 对搜索结果主动限定范围并保留命中位置；本轮不修改官方输出上限，也不添加未经支持的配置键。
4. 提示模型记录已确认事实、已排除方向和下一项待验证假设，减少重复无效搜索。
5. 上述摘要通过提示词要求模型在对话中保留，不新增隐藏状态或消息重写接口，也不把研究笔记写入修复补丁。
6. 保留原始轨迹，便于检查被省略内容是否恰好包含关键线索。

## 需要实现的改动：预算部分

1. 在定位与修改阶段转换时调用 `get_status()`，依据真实剩余时间和调用次数决定下一步，避免无意义高频轮询。
2. 先通过 `eval_config.yaml` 实现显式单题预算，再用提示词研究定位、修改等阶段的分配。
3. 停止策略区分没有进展、工具连续报错和时间不足，保存具体结束原因。
4. 在接近时限时保留提交已有修改所需的收尾时间，数值由 001 实测决定。
5. 通过 `submit_patch()` 提交现有修改；单次命令超时仅返回错误，不等同整题结束。
6. 提交使用官方声明式配置和提示词，不新增任意 Python Agent 控制层。

项目中的“读取窗口”“阶段配比”“收尾预留”是自定义实验变量；四个已确认预算字段只写入 `eval_config.yaml`。
官方 Notebook 显式传入 `EventsCompactionConfig`，不代表正式提交可覆盖压缩参数；评分器支持字段中没有该项。
README 与 Notebook 的压缩间隔分别出现 5 与 15，应记录本地环境实际配置，不把 Notebook 配置宣称为正式评分配置。
实现位置以 001 的配置与提示词为准，优先保持改动可单独启用和撤回。

## 输入与输出约定

输入为固定任务、初始仓库、策略版本、实际可用的预算信息及研究参数表。
最终补丁和官方运行产物沿用 001，不改变比赛提交格式。
研究汇总记录任务标识、参数标签、各阶段时间、停止原因、补丁状态和官方解决结果。
优先读取官方产物 `task_results.jsonl`、`traces/trace_<instance_id>.json`、`logs/<instance_id>.log`，并与 `summary.json` 对照；轨迹结构包含 token usage。
若个别调用的 token 统计或阶段计时缺失，记录“不可取得”及所用代理指标，不能补造数字。
研究统计中的“已生成补丁”“正常结束”和“解决任务”分别记录，不能互相代替。

## 对照设计

| 顺序 | 对照变量 | 固定内容 |
| --- | --- | --- |
| 第一轮 | 基线读取与限制范围的读取 | 定位策略、预算、模型及任务集合 |
| 第二轮 | 是否增加简短的已确认事实摘要 | 使用第一轮选定的读取方式及相同预算 |
| 第三轮 | 不同单题停止条件或时间上限 | 固定上下文策略、定位策略及任务顺序 |
| 后续 | 是否按阶段分配预算 | 固定前述策略，仅改变阶段分配方式 |

一次只比较一个变量，不把缩短上下文和缩短时限同时作为首轮改动。
参数候选由 001 的耗时分布和环境能力决定，在查看本轮结果前写入记录。
各组从干净的初始仓库开始，不继承其他组的搜索结果、摘要或补丁。
比较总预算内完成的任务数时，应保持任务集合与顺序一致，并列出未处理的任务。
官方任务顺序执行；任务具体顺序尚不明确，人工研究先固定顺序，并说明正式环境可能不同。

## 人工运行时记录的内容

- 总墙钟时间，以及能可靠取得的环境、模型和工具耗时。
- 每题开始与结束时间、结束原因，以及停止时是否保留了可提取的补丁。
- 读取次数、重复读取位置、长输出次数和摘要更新次数。
- 实际可取得的 token 使用量；不可取得时可用字符或行数估算阅读规模，并注明局限。
- 因上下文截断遗漏线索、错误摘要或过早停止而失败的具体案例。
- 成功任务所用时间、未完成任务耗时，以及在相同总时间内取得的官方解决结果。

正式评测结果尚未返回时，只报告运行行为和补丁产物，不推断得分改善。
少量样本的平均值容易受个别长任务影响，应同时查看逐题记录与耗时分布。

## 预期产出与结果记录

预期产出包括可切换的上下文策略、预算参数表、逐题时间分析及停止原因分类。
需明确哪些能力由官方环境提供，哪些只是提示词约束，以及约束实际被遵守的程度。
研究结论应说明节约时间是否伴随漏读、过早结束或解决率下降。
实现内容和运行结果写入 `docs/progress/003-budget-and-context.md`，当前计划不创建该结果文档。
有足够证据后再选择用于提交的配置；没有收益的配置保留记录，避免重复尝试。

## 待核实的问题

- 12 小时触顶报错是否已有官方修复，以及实际运行总时间的完整构成。
- 隐藏任务具体数量与顺序是否在运行前可知；单题状态不代表全局剩余时间。
- 可取得哪些 token 用量统计，以及当前部署实际采用的压缩配置。
- 进程强杀或全局中断时的补丁恢复行为，以及官方默认值冲突是否在新版文档中消除。
- 工具调用失败、环境准备失败及模型等待分别如何计入预算。
- 正式运行的 GPU 与研究环境差异，以及这种差异对时间参数的影响。
