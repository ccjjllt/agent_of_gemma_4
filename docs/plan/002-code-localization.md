# 002：代码定位与图检索

## 研究背景

本轮承接 [001：无 LoRA 基线](001-baseline.md)，研究指定模型在修复任务开始阶段如何找到相关代码。
比赛提供基于节点向量的相似代码检索和代码图工具，但工具可用并不等于每次调用都能改善修复结果。
需要在相同任务、模型和资源预算下，测量增加检索方式带来的收益与成本。
本轮不改变模型权重，不引入多 Agent，不同时调整补丁生成策略。
资料核对日期为 2026-09-28；后续资料变化需记录版本，并重新判断受影响的实验条件。

## 研究问题与假设

- 从已知符号出发的相似代码检索可能找到相关实现，但收益需要覆盖调用成本。
- 图邻域可能帮助追踪跨函数、跨文件关系；对局部问题，额外展开也可能增加无关阅读。
- 根据已有线索选择图工具，可能比固定展开所有候选节点更有效。
- 以上均为待验证假设，目前没有本轮实验结果。
- 主办方于 2026-09-26 确认 embedding 空文件问题已修复，但 `async` 函数缺失仍未修复；运行前核对数据版本。

## 前序输入

- 001 的可运行基线、官方资料版本、模型配置及任务运行方式。
- 固定的研究任务清单、初始仓库版本和每题预算；按 `(repo, base_commit)` 分组划分研究与保留任务，禁止同组跨集合。
- 001 的原始轨迹、定位失败案例和可取得的官方结果。
- 官方工具说明，以及当前运行环境实际返回的样例。
- 公开集有 129 题、127 个唯一仓库提交组：FastAPI 67、Rich 48、Requests 13、HTTPX 1；唯一 HTTPX 任务仅作探索。
- 官方图文件提供 `nodes[*].id/name/text` 和 `edges[*].source/target/type/key`；embedding 为对应节点的 256 维 float32 向量。
- 任务中的 `patch`、`test_patch` 仅用于事后研究或人工验证，不作为定位输入。

## 已核实的官方工具边界

以下签名与返回结构已通过官方 `HARNESS_README.md` 第 6.3 节核实，工具返回 JSON 字符串。

| 工具 | 官方签名 | 本轮用途 |
| --- | --- | --- |
| 相似代码检索 | `search_similar_code(query: str, k: int = 10) -> str` | 从已知符号寻找相似代码节点 |
| 邻域查询 | `get_code_neighbors(node: str, edge_type: str \| None = None, max_neighbors: int = 50) -> str` | 扩展已经确认的候选节点 |
| 子图查询 | `get_code_subgraph(nodes: list[str]) -> str` | 检查多个已知节点之间的关联 |

`search_similar_code` 在离线环境解析已有节点键或后缀；应传类、函数或模块名，不能当作任意自然语言检索接口。
相似检索返回 `query/results/count`，其中结果含 `node_name/code/similarity`；邻域返回 `node/neighbors/count`。
子图返回 `nodes/edges/node_count/edge_count`，边含 `from/to/type`；各工具同时返回 `status`，错误含 `error_type/error_message/details`。
优先采用完整节点标识；短名虽支持后缀等匹配，仍需核对解析结果，不能自行把文件路径当作节点标识。
`edge_type` 首轮使用 `None`，实际边类型以当前数据为准，不把文档中的示例类别当作一定存在的边。
普通文本搜索、源码读取及文件编辑继续使用 001 已确认的官方可用工具。
官方 Notebook 另展示 `sg.get_graph/get_neighbor/get_similar_nodes/get_induced_subgraph`，它们是研究库 API，不是 Agent 可声明的工具名。

## 需要实现的改动

1. 在 001 的 Agent 配置与提示词基础上，拆出可替换的“代码定位策略”说明。
2. 保存三套定位策略：文本搜索、文本加相似节点检索、再增加图工具。
3. 所有策略共享问题理解、修改要求和结束条件，避免把提示词整体重写作为隐含变量。
4. 相似检索策略先用文本搜索确认符号，再以该符号查询相似节点；检索结果回到源码核实。
5. 图策略只扩展已有依据的节点；每次展开说明要确认的关系，得到结果后读取相关源码。
6. 多个候选节点均已确认时，再研究子图是否能帮助识别调用链或共同依赖。
7. 对空结果、未识别节点或无关结果记录实际返回情况，随后回到文本搜索；涉及 `async def` 时主动核查源码覆盖。
8. 复用官方现有运行日志；缺少字段时先人工汇总，不假定存在可注入的日志回调。

项目可用 `text`、`semantic`、`graph` 作为实验标签；这些名称是项目自定义标签，不是官方配置字段。
策略选择及参数表应保存在研究配置或说明中，仅将官方支持的字段写入 `agent.yaml`。
文件组织以 001 的真实实现为准，优先新增策略配置和提示词，不提前建设独立检索服务。
本轮不重建官方图；自建图能否进入正式提交尚未确认，不能把本地替换图的收益当作可提交的收益。

## 输入与输出约定

运行输入为 `problem_statement`、官方允许的任务上下文、同一 `base_commit` 仓库、同一模型及本轮选定的定位策略。
中间产物应保留候选文件或符号、信息来源、调用顺序，以及从检索结果转到源码的过程。
最终输出沿用 001 的官方补丁与结果产物，不新增未经确认的 Harness 返回协议。
官方结果目录已有 `summary.json`、`task_results.jsonl`、`patches/<instance_id>.patch`、`traces/trace_<instance_id>.json` 和 `logs/<instance_id>.log`，按每组运行分别保留。
人工汇总表可使用以下项目字段：任务标识、策略标签、候选位置、定位耗时、检索次数、结果来源和失败类型。
汇总字段仅用于研究记录，不代表官方任务 schema 或工具返回字段。

## 对照设计

| 组别 | 可使用的定位方式 | 主要比较 |
| --- | --- | --- |
| A | 001 已有文本搜索与源码读取 | 参考基线 |
| B | A 加相似节点检索 | 相似代码检索的增量作用 |
| C | B 加邻域及子图查询 | 图工具的增量作用 |

各组固定模型、任务集合、初始仓库、预算、其余提示词及可配置的生成参数。
先在少量任务上人工确认配置生效和日志可读，再扩大到 001 确定的研究任务集。
不要把不同策略生成的补丁、轨迹或中间结论传入下一组的任务运行。
如条件允许重复运行，应先固定重复次数，并分别报告各次结果，不能只挑选最好的一次。
第一轮先比较三种方式；是否按任务类型选择工具，留待观察到稳定现象后另做对照。

## 人工运行时记录的内容

- 每题最终官方结果；若尚未取得，明确写“未取得”，不要用补丁已生成替代解决成功。
- 从开始处理任务到首次找到经源码核实的相关位置所用时间，以及整题总时间。
- 相似检索、邻域、子图与文本搜索的调用次数，各次查询和实际返回内容。
- 重复搜索、无关读取、空结果、工具错误及随后采取的回退方式。
- 图展开是否引出了新的相关文件，以及这些文件是否实际参与后续推理或修改。
- 定位完成后仍然失败的原因，区分定位问题与修改、运行环境、时间耗尽等问题。

定位相关性由人工结合任务与源码复核；不能简单把修改了某个文件当作正确定位。
若无法可靠取得 token 数量，可记录实际读取的代码行数或字符数，并注明这只是代理指标。

## 预期产出与结果记录

预期产出包括三套可切换定位策略、同任务对照轨迹、逐题记录及典型失败案例。
主要判断依据为最终解决结果与整题时间，定位速度和检索次数用于解释变化。
少量任务只支持提出后续假设，不足以证明某种检索方式普遍优于其他方式。
实现内容与实际结果写入 `docs/progress/002-code-localization.md`，当前计划不创建该结果文档。
若 C 无增益，应保留失败证据，再判断是调用策略、任务类型或信息成本所致。

## 待核实的问题

- 当前下载版本中的实际边类型、短名歧义及各研究任务的索引覆盖情况。
- `async` 缺失问题是否出现后续官方修复；不能把 9 月 26 日状态无限延伸。
- 各工具调用的实际耗时、输出长度与超时行为。
- 官方支持按 `tools:` 附加工具子集；需人工检查各组实际工具列表与预定分组一致。
- 公开开发集与隐藏私有仓库的差异；公开集收益能否迁移尚无结论。
