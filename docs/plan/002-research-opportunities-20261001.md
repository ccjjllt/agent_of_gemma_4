# P002 等待算力期间的研究结论与实现交接

日期：2026-10-01。目标：提高最终隐藏私有仓库的修复率，争取金牌与奖金。本文完成历史数据再分析、官方信息核对、文献机制筛选和下一候选规格；**候选尚未实现或运行，没有新增成绩**。大量实现交用户完成。AMD 暂缓，TPU 停止，不启动新的远程算力。

## 1. 方向决策

P002 主问题保留，但下一步重心从“更多办法找到文件”移向 **相关源码证据 → 正确的故障假设 → 可执行的小修改**。

按顺序推进：

1. 已冻结的 T0/T1 六题、12 attempts 照原名单运行，回答现有导航技能是否有用。
2. 首选新候选 **T2：读取片段句柄 → 精确小范围编辑**。解决已经看见源码、却在复制旧串和反复编辑失败中耗尽预算的问题。
3. 第二候选 **T3：有区分力的最小反例**。当复现与 issue 不一致时，改正故障子条件，避免围绕一个没有触发缺陷的脚本空转。
4. 第三候选 **T4：分层代码概览与有限批量查询**。服务于尚不能得到有用函数/分支证据的题，不强制图检索。

T2/T3/T4 是本文提案编号，不是已存在的 frozen variant。逐项比较，不将三项一次打包后宣称某个机制有效。原 T0/T1、0C 的16384选择、原始失败标签与结果文件保持原样。

## 2. 新证据为何改变优先级

本轮联合分析 P003 的69次运行和 P002-0C 的24次运行：93份结果、92条可用轨迹、27个已暴露任务；缺失一条成功轨迹，67条失败轨迹均有记录。来源与脚本见[机制研究](../../research/002/mechanism-study-20261001/README.md)、[逐次证据](../../research/002/mechanism-study-20261001/evidence.json)。

| 新观察 | 能支持的判断 | 不能推出的结论 |
|---|---|---|
| 67次 raw 失败中，61次成功 `read_file` 了参考补丁涉及的文件；覆盖21个不同task_id，失败总计24个task_id | 单看“最终没有生产补丁”会把不少后续行为问题误记成纯文件定位失败 | 不是91%的任务已定位正确或理解根因；同一大文件可能读错位置，重复 attempts 不独立 |
| 54次失败的成功读取包含参考补丁删除行中的长文本锚点 | 部分失败已得到更细的文本接触证据 | 锚点只是去首尾空白后长度≥20的删除行子串，可含通用代码；不等于正确函数覆盖或语义理解 |
| 61次文件命中失败中，37次没有成功的直接 `edit_file/write_file` 生产编辑 | 值得研究证据怎样转为实际编辑 | shell修改未计入；不能称37次完全没改源码 |
| 同题 `fastapi_14873` 的0C四次运行约26秒都读到相关区域，结果两成两败 | 查找速度本身不足以解释胜负，应看之后的假设与动作 | 不证明这些运行具有相同内部理解 |
| `rich_2725` 成功例是短小索引交换；失败例反复较长旧串替换，七次找不到旧串 | 编辑粒度和接口是可操纵的研究变量 | 一个案例不能证明句柄接口会提升总体修复率 |

另一项必要的反证：67次失败只有28次尝试过直接生产编辑，12次遇到直接编辑错误，分布在6个task_id；错误调用大量集中于少数题。[分层统计](../../research/002/strategy-review-20261001/derived-metrics.json)。**T2不能解释所有“读过但没修好”**，不应把37次未成功编辑都算成它能救回的案例。T2先实现，是因为干预具体、CPU能验证工具行为；T3可能作用于更早的错误假设，潜在覆盖尚待测量。T1也已经提示编辑失败后回读，须先观察它是否足以改善这些案例。

参考修复的离线规模画像：27题中18题只涉及一个非测试文件，19题总增删不超过20行，中位12行；也有最大259行的任务。非测试文件包括文档/示例，增删行数不等于语义难度。此统计支持优先准备小范围编辑能力，不应强迫所有题只改一行。问题描述中直接出现参考文件 basename 的仅4/27，因此不能把“从 issue 抄文件名”当完整定位方案。[画像与复算脚本](../../research/002/opportunity-profile-20261001/reference-scope.json)

**历史结论不重写：** P003 B 面板仍是3/24对3/24；0C仍是7/12对6/12并保留16384。以上数据只重新解释机制，不是新策略得分。后一次0B的 eligible 标签不能反向证明历史运行环境有效；`requests_6644` 的 raw 通过也不能当作修复增益。

## 6. 交用户实现：T2读取句柄与精确编辑

### 研究假说

当模型已拿到待改源码，重复生成旧串增加了转义、缩进、截断、匹配歧义和输出成本。由读取工具保管精确原文，模型只生成新文本，可能提高同预算下的成功源码编辑率。它不会自动修复错误逻辑，也不解决全部JSON编码问题。

### 最小接口

```text
inspect(path, start_line, end_line)
  -> status, span_id, source_sha256, actual_range, complete_text,
     truncation, next_range

apply_span(span_id, replacement)
  -> applied | stale_source | invalid_span | invalid_replacement,
     changed_lines, compact_diff, updated_span_id
```

实现为一个 ADK skill，复用现有 `run_skill_script`，不新增host工具注册，不重写评估载体。`inspect`返回的代码与原导航读取保持相同范围/顺序，首次实验研究编辑接口增量。入口可采用同一脚本的 `inspect/apply` 子命令，模型面对两个稳定动作即可。

实现细则：

1. 句柄绑定本题实例nonce、仓库身份、相对路径、文件字节哈希、行对应字节区间与原始字节。只允许编辑实际完整展示的片段；不可见、半行截断或省略过的骨架不生成可编辑句柄。
2. 辅助状态放在**执行沙箱**的本题临时目录，跨技能调用可读，结束后清理；路径由代码构造，不能让模型指定任意状态根目录。不能放在每次调用释放/回收的skill目录，不能仅凭cwd认定任务仓库。通过实际沙箱执行适配解析任务root，首次访问创建并后续复用nonce；键包含root身份、HEAD和该nonce，下一题不得复用。状态不进入 `git diff`，也不读宿主模型/数据目录。Docker与本地subprocess的状态位置由实现者据实际沙箱映射选定，不假设宿主 `/workspace` 就是题目仓库。
3. 编辑前按文件哈希确认原文未变；stale时返回“重新读取”，不模糊匹配、不猜测反转义、不扩大替换范围。UTF-8解码失败明确返回；保留未编辑字节与换行风格。
4. 初版每次单区间、单文件原子写入；替换文本由Gemma完整提供。若需要多个区间，先逐个重读再改，暂不建设复杂事务调度器。
5. 成功后立即返回精简diff与 `post_source_sha256`；读取时的 `source_sha256` 明确为编辑前哈希。仅在更新片段可以完整展示且总JSON不超限时签发 `updated_span_id`，否则置空并给建议重读范围；任何裁剪展示都不能拿来继续精确编辑。失败不留下半修改。返回完整合法JSON，按序列化后的总长度控制输出，不截断JSON字符串。
6. 编辑作用域按生产源码限制；兼容必要的新生产文件可继续使用官方 `write_file`，不要求所有动作都走句柄。不要把脚本变成自动代码生成器或模糊自动修复器。

状态位置的源码依据：已读google-adk1.36.1的`skill_toolset.py:625–709`在`TemporaryDirectory`中释放技能、切换cwd、执行后恢复；正常退出回收临时目录，不保证强杀后清理。该链的脚本参数与swegemma0.2.7的`agent_runner.py:327,392`没有自动注入本题nonce；这不代表无法取得身份，而是实现需要根据经确认的沙箱root建立自己的持久nonce，不能依赖未声明的注入。

建议文件结构（新增目录，**不是改冻结T1**）：

```text
research/002/candidates/t2_span_edit/agent/
  agent.yaml                         # 继承已选公共底座
  prompts/system.md                  # 只增句柄读取/编辑的短用法
  skills/source_edit/SKILL.md
  skills/source_edit/scripts/source_edit.py
  skills/source_edit/scripts/span_store.py
```

具体比较：T1 与 T1+句柄编辑保持相同导航策略、读取范围上限和模型预算，才能解释为**编辑接口组合**增量。该组合同时包括旧串引用、过期校验与编辑后反馈，不能单独证明“不复制旧串”的收益；若以后研究该细分机制，双方需相同反馈，只切换旧文本引用方式。若冻结T1显示技能几乎未被调用，则先报告“不发生足够干预”，根据实际调用原因修订技能入口，再单独运行；不能用T0对“导航+编辑”的差值全归因于编辑。

需要记录的研究量只有：实际技能使用、失败编辑链、成功生产编辑、终局修复、耗时/输出量。准确的首个编辑时间来自成功回包或真实diff；更早编辑本身不等于正确率提高。已有数据中能同时观察到文件命中与成功直接编辑的失败24次、成功21次，中位间隔约125/132秒；这是条件子集，不能据此讲“成功因为改得早”。

## 7. T3：让复现真的回答当前问题

T3与T2分开。先做提示/技能资源的小增量，不需要新增测试框架：

```text
当前观察：这个复现是否真的包含 issue 的触发前提？
关键区别：只改变哪个输入/配置，就应从正常转为异常？
预期差异：异常类型、返回值、格式或分支应出现什么区别？
已有证据：在哪个源码分支/实际输出中看到了它？
```

当复现意外通过或连续无信息时，最多补一组有依据的最小对照；不是每题强制先写测试。若依赖/fixture报错、尚未到断言，不能当作复现成功；可以用源码证据继续推理，不为验证而修环境。临时复现放沙箱临时目录，不写入最终补丁。

目标是让模型改变错误假设，不只是换一个脚本文件名。最终依据是题目修复率；“通过了自己写的测试”仅是局部证据。不要加一个LLM裁判，也不要把参考答案或裁判测试预装进技能。

收尾作为后续独立子假说：生产diff存在、所需对照完成且没有未解决矛盾时提交；缺少证据则明确保留不确定性。P003固定最后20秒收尾并未胜出，因此这次研究的是证据驱动停止，不是换一句倒计时提示。初版T3先只测反例构造，不同时改收尾策略。

## 8. T4与训练准备只做有价值的部分

T4可在CPU上完成实现规格或原型：`outline`先返回目录与定义签名，`locate`允许2–4个有来源的相关查询，`inspect`展开少量完整函数。保持≤8候选与共享输出预算；不能把前400字符当完整函数、不能把裁剪展示当精确编辑输入。不新增神经向量模型。是否启动T4在线实验由T0/T1轨迹说明：仍缺相关证据，还是拿到以后不用。

LoRA目前准备**数据而非训练**。从既有轨迹分离四类片段：有效定位、成功小编辑、真实错误恢复、假设被输出推翻后的转向。每个样本保留当时可见输入、动作、回包、步骤号和最终验证状态；离线gold弱标签单独保存。不要将删去失败动作后的后文直接拼接成不存在的“成功轨迹”，不要把分析者建议伪装成Gemma真正做出的恢复。

学习数据数量按独立issue/repo/commit计，不按93次重复运行夸大样本量。参考patch可用于开发诊断；候选运行只读取正常issue和本题源码。外部数据暂查论文、许可与任务元信息即可，不急于下载大语料或调用教师生成。
