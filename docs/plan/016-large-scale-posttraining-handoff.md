**2．把“单位时间提高能力”变成能决定下一笔投入的指标。**

第一目标是固定比赛预算下的真实修复能力，研究效率看其增量相对总日历时间：

`研究效率 = 同协议修复率的可信增量 ÷ 从开始准备到取得可信比较结果的实际经过时间`

这不是声称可精确预测的优化公式，而是取舍原则。实际经过时间包含准备、训练、排队/恢复和评估造成的等待，但并行时段不重复相加；计算成本另记。训练 token/s、监督 token/s、GPU 利用率和 loss 都是诊断量；高吞吐若只在学习重复读取，仍可能没有能力收益。官方分数是通过问题的比例，不能自行改成“修复数/小时”；推理耗时用于判断同一方案能否在整场预算内完成更多题。

每次只汇报四类实数：去重独立问题与行为覆盖、有效训练 token 与端到端耗时、同题新增修复/回退、实际提交分数。对训练耗时同时记墙钟、GPU 卡时和平台配额，三者分开；Kaggle 历史余额与 P015 的 14h 上限不自动成为新租卡或新大作业的预算。

新来源的价值是有机会降低每个有效训练问题的整理成本，不是数字更大。Open-SWE-Traces 与 SWE-rebench 等也有来源重叠，不能和 SWE-Lego 简单相加。若它的适配产率明显更高，可替换主混合中的低效来源，不必同时维持四套全量生产线。

**数据规模建议：**第一轮主训练争取 5,000–10,000 个去重合格问题；首个连续训练版本可从约 1,000–2,000 个有完整或有意义阶段覆盖的问题启动。两者都是规划目标，不是已拥有数量或开训硬门槛。先用各源约 100–200 个按元数据分层选择的候选估计有效产率；若真实产率更低，应修改来源、适配或长度方案，而不是复制小样本凑数。当前 3 题数据只能作为补充。

**5．整理过程以有效产出为中心，先隔离身份，再读取与筛选正文。**

1. 固定来源 revision、许可、教师、原 harness、问题/轨迹身份，优先复用已有下载和 tokenizer 缓存。沿用历史 train/dev/select/预留用途；对新的确认面板先按身份元数据分配仓库家族。禁止为扩量把旧评估题转成 train，不读取 heldout 内容。
2. 合并同一仓库及 fork、同一问题、base commit、补丁近重复和同轨迹多格式版本。先身份去重，再对已分配 train 的内容做近重复；跨仓评估按仓库家族整体隔离。每个问题第一遍优先一个合格轨迹，额外轨迹只有增加有效恢复或解法覆盖时才保留，并限制总权重。
3. 排除无可信成功记录、参考修复泄漏、读取未来提交、git hacking、删断言/跳过验证作弊、消息断裂和不可恢复的工具状态。正常修前复现失败、合法新增回归测试不能仅因失败退出码或改了测试文件而被判作弊。项目自身仍不新建测试套件。
4. 在合格池内按仓库、缺陷/功能需求、单/多文件、长度、恢复与验证行为分层选择。先正确性和过程有效性，再在同类中偏好较少冗余的轨迹；不能全局只选最短、最容易或最强教师的数据。目的明确的读取是训练内容，不能只留下编辑。
5. 输出同一个数据版本的实数：独立问题/仓库/轨迹数、原始与转换后 token 分布、监督 token、编辑/验证/恢复/结束覆盖、8K/16K/32K 可用比例、过滤/去重/转换损耗。比例按监督 token 和独立问题同时报告，不以切片数代表规模。

第一轮不固定 Real/Synthetic 的机械比例，也不混入大批通用聊天、数学或算法题。若后续观测到通用指令能力退化，再用少量有根据的保留数据处理。对长轨迹限制单问题的总采样权重，避免一题的多窗口或冗长 reasoning 主导全局 loss。

作者已有可靠执行证据且转换无损时，复用原证据并做分层人工抽查；不要求全部由 Gemma 重解。初版每个转换类别抽查约 10–20 条，覆盖成功、恢复、终局、最长窗口；这是准备工作的起点，若发现系统性错误就修该转换规则并重建受影响分片，不新增独立检查工程。缺乏证据或改变执行语义的样本按下一节处理。

**6．工具适配与长上下文共同决定产率，不能只改函数名。**

原轨迹永久保留；转换版本逐动作记录原调用、目标调用、工作目录/文件状态、观察出处和 loss 位置。OpenHands/SWE-agent 的 shell、编辑器、退出方式与比赛六工具并不天然等价。

| 转换类别 | 如何处理 | 能声称的证据 |
|---|---|---|
| 调用与反馈语义不变，仅结构化序列化 | 核对 cwd、环境、超时、输出边界和调用配对，复用来源执行记录 | 来源执行成功、转换后语义保持；不是本项目重新解题 |
| 改变编辑工具、状态或观察形式 | 在原 buggy 状态重放受影响动作；下游消费新观察时核对后续依赖 | 仅把实际重放范围写成已验证；局部通过不升级成整题成功 |
| 不能可靠映射，或状态缺失 | 第一版暂存，不伪造成功回包；先收录其他高产类别 | 无训练成功声明 |

模型必须在目标 Agent 的输入中确实见过足以支持动作的信息。不能从 gold patch 自动定位一段源码，再声称训练了自主定位；这种局部材料可以单列辅助用途。也不能为展示“验证—提交”完整链而补写没有发生过的命令或终局。

长度处理按以下顺序：

- 转换后能容纳的完整轨迹优先，一次前向监督多个有效 assistant 回合；不为每个短动作复制完整前缀。
- 超长轨迹优先使用来源真实模型请求、真实 compaction 后状态和相应后续动作。使用与部署等价的模板；需要重复前缀的窗口仅监督尚未计入的目标，避免同一动作重复加权。
- 原始历史未发生压缩、且后段超过上限时，不直接截掉前段，不用未来补丁生成摘要。只做格式上的无损精简也必须确认没有改变当时可见信息。新摘要或新阶段入口需从新状态检查并必要时重新续跑；这不是第一轮全库必做步骤。
- 没有可信短状态的长尾保留为后续池。若大量编辑/验证因此丢失，应先比较更易适配的来源与真实长序列成本，不能把训练集退化成只有导航动作。

32K 是候选上限。按自然长度分桶，测 8K/16K/32K 的真实输入，不把短样本填充成 32K；不预设各桶比例。第一版优先复用已有长度分组，只有 padding 已证实为主要浪费时才增加跨样本 packing，并保证独立样本的 attention 隔离、位置和 loss 边界正确，不能直接拼接互相看见。

**7．学习完整有效行为，同时保持 Gemma 真实的回合与思考边界。**

主要监督目标覆盖“理解需求—定位—修改—运行有效检查—读取反馈后纠正—正确结束”。不是每道题必须机械走全流程，但整个训练池不能缺编辑、验证或终局。

| 内容 | 初始处理 |
|---|---|
| 系统/用户输入、源码、工具返回 | 作为上下文，loss mask |
| 有价值的 assistant 分析、合法调用、有效编辑、检查与正确结束 | 正向监督；保留来源和可见状态 |
| 已确认错误的工具名/参数/无效重复动作 | 保留必要错误及反馈上下文，mask 错误动作；监督后续有效恢复 |
| 修前复现的预期失败，或修后检查揭示仍有缺陷 | 不因非零退出码而自动 mask；这是有用的检查行为 |
| 最终失败轨迹 | 第一轮不整条当成功示范；局部有效片段只有证据明确时才另用 |

[SWE-Lego](https://arxiv.org/html/2601.01426v1)支持保留错误上下文、屏蔽错误动作的做法；其原实验是 Qwen 系列 **128K 全参 SFT**，不能据此承诺本项目 32K QLoRA 的收益。[Terminal-Lego](https://arxiv.org/html/2606.03461)则提醒：更强教师未必教得更好，有目的的观察动作本身也值得监督。这里只迁移数据设计原则，不搬用论文得分。

不要把当前 `thought_loss=mask` 永久当作最优，也不要把全部冗长教师 thinking 一律纳入 loss。初版以可支持目标动作、边界明确的分析与调用为主；来源没有 reasoning 就不编造。若同类数据有大量冗余思考，优先选原本较有效的轨迹，而不是任意删改中间推理制造新历史。

Google 官方区分普通跨回合历史与同一 model turn 内的工具链：前者处理历史 raw thoughts 的方式与后者不同；无 thinking 数据还有空 thought channel 的建议。最终以比赛固定 CT 模板与实际 wire 请求为准，人工展开几种真实编码观察标签。现有编码器会拒绝部分非工具 final 的 reasoning 组合，需补齐或用实际合法边界表达，不能静默丢失结束能力。[Gemma 4 官方格式](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)、[现有编码器](../../training/encoding/gemma_tool_chat.py)

单条序列的多个监督回合仅在其因果前缀与实际可见历史一致时合并；若模板会删除旧思考或发生 compaction，应使用分段真实状态。减少重复前缀不能以引入未来信息为代价。

**8．训练准备只补影响持续计算的缺口，保留已成功的实现。**

起始配方如下，属于可调整的研究起点，并非最优参数声明：

| 项目 | 初始选择与理由 |
|---|---|
| 模型 | 官方 31B QAT 来源、现有可追溯 NF4 缓存；部署仍用官方 31B CT v2＋独立 adapter |
| 更新 | QLoRA，先沿用已成功 r8/alpha16 和 q/o＋MLP 目标模块；不同时改变 rank、数据与 Agent |
| 多卡与数值 | 现有 FSDP、BF16、梯度检查点、selected_chunked loss；固定成功依赖版本 |
| 学习率与遍历 | 从现有 2e-5、1 epoch 起；warmup/scheduler 依据冻结的有效 token 预算或总更新数设定 |
| batch | 每卡 microbatch 1 起，四卡累积 2 可作为已知起点；记录实际全局序列数与监督 token，不能只写 batch=8 |
| 长度 | 自然长度分桶；上限由编辑/验证/结束覆盖及实测吞吐决定，16K/32K 是目标而非既有成果 |
| 检查点 | 可恢复训练状态与独立部署 adapter 分开保存，低频导出评估点 |

FSDP-QLoRA 对量化存储 dtype、包装方式和 metadata 有要求，现有实现已处理相关问题，不为升级框架重新做一遍。NF4 训练与官方 CT 推理仍存在量化差异，因此 loss 改善后必须回 CT 看行为。[bitsandbytes 文档](https://huggingface.co/docs/bitsandbytes/main/fsdp_qlora)、[PEFT FSDP 文档](https://huggingface.co/docs/peft/main/accelerate/fsdp)

**续训是本轮明确必须完成的功能。** 保存 LoRA、FSDP 对应的 optimizer 状态、scheduler、global step、每 rank 随机状态、数据版本/采样顺序/下一个 batch 游标及累计有效 token。最好在 optimizer step 边界保存，避免还需恢复未完成梯度累积；采用完成标记与原子落盘，保留上一份完整 checkpoint。冻结基座无需每次重复写出，但其身份与缓存要能完整恢复。新数据批次固定版本后再开始新阶段，不能续训时悄悄改数据顺序或重启学习率。

用同一小批 train 数据手动完成一次“更新—保存—退出进程—重载—继续更新”，对照未中断路径的下一批身份、LR、优化器状态和参数更新合理一致；不要求跨硬件逐 bit 相等。复用当前 PyTorch/FSDP 版本对应的状态 API，不把最新文档示例直接复制到旧运行环境。[PyTorch 分布式 checkpoint](https://docs.pytorch.org/docs/stable/distributed.checkpoint.html)

保存频率根据实测写盘时长与最多可接受重算量选择，建议先按约 30–60 分钟运行量估计，再调整；Kaggle 会话结束前预留导出与持久化时间，保存到 `/tmp` 不算跨会话恢复。短恢复核对是一次性手动实验，不新建 tests/check/gate 项目。

**9．4×48GB 的选择标准是有效吞吐，不是能跑的最长序列。**

机器到位后记录确切 GPU 型号、互联拓扑、CPU/RAM、磁盘和缓存位置。在本轮数据的短、中、长真实样本上做少量连续更新，包含最长桶和保存/恢复；测冷启动、峰值、有效输入/监督 token/s、padding 与重复前缀、独立问题/小时、checkpoint 开销。当前三步 L4 容量实验的速度不能外推四张 48GB 上的长轨迹吞吐。

FSDP 是默认起点。已有 DDP 可在单卡放得下代表性长样本时作一次限量对照：48GB 上复制冻结基座可能减少分片通信，但是否更快取决于余量和拓扑；不预先保证。若 QLoRA 的解量化或通信确实成为主瓶颈，才考虑一次 BF16 LoRA 对照，不为这件事先造新框架或扫描多种并行方案。先解决数据与续训，再决定这类优化是否值得。

首日测量后计算：`预计训练墙钟 ≈ Σ(各长度桶实际训练 token ÷ 对应端到端吞吐)＋必要评估/恢复`。同一桶的 token 口径必须一致；监督 token/s 受 mask 密度影响，不跨不同密度样本直接外推。真实数字出来前不承诺“几小时训完一万题”。

若 32K 代价过高，优先用能覆盖完整行为的较短轨迹开始训练，给确实需要长状态的样本留独立预算。若较短桶几乎只剩读取，必须修数据来源/适配或资源方案，不能把它当有效降级。不开 128K 容量专项，不继续孤立算子优化直到有整模瓶颈证据。

**10．正式训练采用一个连续主实验，少数预定评估点。**

第一段是运行校准：用几十条覆盖主要长度、编辑/验证/恢复/终局类型的真实 train 样本确认 loss 标签、实际更新、恢复和 CT 导出。它不承担泛化判断，样本保持 train。已有小 RFT 结果可以参考，但不必为再次证明三题能拟合重开同样实验。

第二段是公开轨迹主训练：固定第一版数据与一个起始配方，先遍历一次。可在约 10%、50%、100% 的预定有效训练量导出候选；只让最早候选做运行退化筛查，中期与终期进入修复比较。评估由独立资源或明确时段承担，不每几十条样本就停下来改方向。一个 epoch 不代表自动达到所需规模，实际训练量按独立问题与 token 同时报。

预定检查点若发现可复现的系统性运行或修复退化，暂停后续更新并排查原因，不机械跑完这一轮；单题波动不触发改配方。这是执行阶段的止损规则，不增加评估频率或新建检查体系。

第三段是有针对性的协议适配：只有主训练后的诊断显示工具参数、编辑恢复、compaction 后继续执行或结束行为仍明显薄弱时才做。优先用已可靠转换的公开轨迹，补少量 Gemma 在 train 问题上的真实成功/恢复。当前三题不要重复复制成主要数据；适配结束仍比较真实修复，防止小尾段冲掉主训练收益。

若训练侧拟合仍差，先排除标签/模板/优化器/学习率等问题，再决定是否加数据、训练量或 rank。若训练侧明显改善而 CT 不改善，先检查迁移与行为分布，不立即加 epochs。rank8 只是已验证起点，不是规模化训练容量足够的结论。

**RL 暂放到后续决策，不作为 SFT 前置工作。** 只有规模 SFT 已形成可复现基线、剩余错误适合通过真实执行反馈改进、环境与采样供给有足够吞吐，才值得用独立预算试一条 RL 路线。[LEGO-RL](https://arxiv.org/html/2608.17393)对真实生成流与压缩状态对齐的研究值得吸收，但其 rollout 成本也说明在线 RL 不是当前单位时间收益的当然优选。公开教师成功轨迹上的 SFT 是离线蒸馏；本项目按成功采样筛选后做交叉熵更新仍是监督式更新，不能冒称已经做策略梯度 RL。

**11．评估服务于选择权重，保持 Agent 固定。**

直接复用 [P015 协议](../../research/015/protocol.json)：六工具、5 分钟、28 次工具、40 turns、单命令 60 秒、temperature 0.2、top_p 0.95、输出上限 8192、thinking 4096。训练期间不同时改提示、工具、上下文压缩策略或多 Agent 架构。A/B 同题、同服务设置、同并发、同预算，仅换 adapter；交替顺序，保留全部成功、失败、超时与环境错误。不能把历史 base 5/12 直接减去今天 adapter 的结果称为净收益。

现有 12 题只做开发筛选。主候选形成后，在训练前已按元数据留出的 **新增 24–32 题、多个训练外仓库家族**上做确认；它们与用户已有 heldout/预留题分开，不能借机读取或消耗既有保留集合。优先复用来源已有 F2P/P2P、项目已有回归与官方 harness；新面板先确认环境和判据可执行，不新建专用测试套件。对没有可靠回归证据的任务单列结果范围。

12 题全量 A/B 共 24 attempts，按每次 5 分钟为约 2h 串行 Agent 上界；32 题两臂为约 5h20m，另加服务与准备。研究并发墙钟与正式串行预算分开。数据/训练负责人不能提前花掉确认评估所需预算。

对每个候选列新增修复、回退、共同成功/失败、超时、模型生成量和耗时；若差异只来自一两个不稳定任务，预定复跑或增加独立题，不能不断挑最有利 checkpoint。官方每天一次提交、最终选两次的限制也不适合把公榜当高频调参器。[官方规则](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules)

现有六个超时任务约 99.8% 的 Agent 时长落在模型 API 区间，包含排队/prefill/传输，不能全部归为 thinking。训练数据应少学重复推理和无效动作；待权重比较完成，才用同一面板对胜出权重做一次独立低 thinking 预算实验。选择的是时间预算内修复最好的点，不能预定“越短越好”，也不能把这部分收益算成权重收益。

正式候选还要在官方 CT 服务配置下确认实际 adapter 路由、运行容量和串行耗时；保留官方基座，不合并成另一套重导出权重。仅在真实净收益且部署可承受时升级候选；否则保留正式 0.15 基线，按主要失败原因修改下一批训练，不为满足日期反复提交。

**12．准备期按并行交付组织，避免继续停留在小样本实验。**

下列时间是资源就绪后的目标工作窗口，不包含未知租卡、排队或许可处理时间；不是训练工期承诺。

| 时间窗口 | 数据负责人 | 训练负责人 | 评估/统筹负责人 |
|---|---|---|---|
| 0–6 小时 | 固定来源与身份隔离；各源分层抽样，给出长度/可转换产率 | 复用缓存和成功环境，明确续训改动与真实样本需求 | 收回 P015 已有回执；固定预算、同 Agent 协议及新增确认题的身份划分 |
| 6–24 小时 | 完成最有产率的工具转换；交付首批可训练分片及覆盖报告 | 完成可恢复 checkpoint；在目标机器测真实桶吞吐与一次恢复 | CPU 准备来源既有判据；估算全量 A/B 成本并预留 |
| 24–48 小时 | 形成第一版有实质规模的冻结语料，后续分片继续整理 | 用短运行校准后启动连续主训练；给出基于实测的结束时间 | 早期候选只排查明显运行退化，不频繁改目标 |
| 第一轮结束后 | 按独立 train 错误分布准备必要补充，不使用 dev 解题内容造训练样本 | 主候选与必要短适配候选；保存可恢复状态和部署 adapter | 同期 A/B、新面板确认、正式运行成本核对；形成下一笔训练投入依据 |

主实验开始前应有五项具体交付：可追溯的冻结数据版本、真实 Gemma 编码与行为覆盖报告、目标机器实测吞吐、完成一次进程重启续训、可运行且预算已预留的同期权重对照。它们是避免整轮训练浪费的实际条件，不扩展成新的门控/审计系统，也不要求先证明模型已提分才能进行主训练。

第一天如果仍只有几题/几十个动作，优先解决数据源和转换产率，停止重复自产采样；如果大量时间耗在少数复杂编辑器映射，暂时跳过那类，先训练可信的可转换部分；如果有效语料已经充足，停止继续搜新论文和新框架，进入主训练。除了修复会破坏数据或运行的缺陷，不在中途同时扫超参数。

**13．交给下一位执行者的直接任务。**

> 沿本方案准备 Gemma 4 31B 的大规模轨迹 SFT。先收回 P015 既有作业结果并复用其缓存、协议、开发载体；不要重复启动旧作业。以 SWE-Lego Real/Synthetic 与 SWE-smith 为主，限量比较 Open-SWE-Traces 的 Python 成功子集，先隔离评估身份再读取 train 正文。批量产出可追溯、语义正确、覆盖编辑/验证/恢复/结束的训练分片，减少逐动作重复前缀。补齐 FSDP 真续训与普通 final 编码，在用户选定的 4×48GB 上用真实样本测吞吐，再冻结第一版数据和配方持续训练。只在会话授权与明确预算内启动 GPU；租卡或购买资源不由本文自动授权。训练和数据准备并行，但新分片按版本进入后续阶段。固定 Agent 做同期权重 A/B，用训练外确认面板决定是否扩大训练或进入短适配；不把 loss、导出或局部重放当成提分，不读取 heldout，不新建测试体系。

本方案对 P015 的核心调整是：**从低产率的自产短动作积累，转为高质量公开轨迹的批量供给；从“能跑多长”转为“每小时学到多少有效修复行为”；从训练完成转为同预算真实净新增修复。** 暂停新的多 Agent、技能、图检索、全量教师重采样、并行 RL 路线以及无依据的多 epoch 扩张，把准备和计算集中到这条链路。
