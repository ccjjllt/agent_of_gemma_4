数据负责人先按仓库/问题/基准快照元数据划分用途，再读已分配的内容，合并 fork 和重复问题。沿用既有 select、dev、预留题隔离，不重分配已看过的评测题。首轮继续筛 64–128 个独立问题，但先交付一小批可重放、可编码的完整素材；记录独立问题数、仓库数、轨迹数、真实恢复数、输入/监督 token 分布和可训练覆盖比例，不能把多个切片当作多个问题。

尤其注意：历史 **6,032-token 样本属于 select transaction**。下一轮连续参数更新必须另选 train 划分中的真实样本；即使仅为容量实验也不能对 select 样本做优化器更新。

SWE-Lego 是优先素材来源，但新增 GPU 采样尽量用我们实际提交的 **31B + 同一协议**，在训练仓收集“当前模型会犯的错→真实反馈→成功恢复”。这能减少只模仿其他教师长轨迹而没有覆盖 Gemma 失误的偏差。公开数据的来源、许可和教师身份如实保留；现有官方外部教师讨论未见明确裁定，公开数据使用与主动购买闭源教师生成数据是不同事项。本轮无需把新增闭源教师作为前置条件，也不把未裁定解释成已禁止或已许可。[官方讨论](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/749585)、[已读归档](../../research/007/official-data-20261017/report.md)

素材实际应覆盖以下行为，比例服从可用证据，不为凑标签伪造失败：

| 训练能力 | 必须看到的执行事实 | 容易误收的数据 |
|---|---|---|
| 定位并完整修复 | 读到支持修改的源码，处理关联分支/调用契约，已有行为检查支持修复 | 未观察实现就给出参考补丁；只修表面例子 |
| 编辑恢复 | 参数/锚点失败后重读当前状态，改变操作并成功编辑 | 只给同一成功补丁贴 `recovery` 标签 |
| 命令与语义恢复 | 区分坏命令、环境故障和真实代码缺陷；修后失败后再次改源码并复用同一有效检查 | 将 SyntaxError、未执行或超时当修复验证通过 |
| 正确结束 | 证据已充分、最终 diff 与实际文件一致，提交并合法终止 | 通过后反复验证；把“非空补丁”当正确性证据 |

保留正常的一次成功轨迹，避免把所有任务都训练成必须先犯错再恢复。保留错误动作及工具反馈作为上下文，mask 已确认错误的 assistant 动作；修前有意义的复现失败仍是正确动作，不因返回非零而屏蔽。重复无效调用不重复计正向监督。不要用参考修复改写“当时推理”，再声称是自主轨迹。

从 OpenHands 转到比赛工具时重放实际文件状态、编辑和命令结果，不只重命名工具。编码使用真实 CT tokenizer、chat template、工具 schema；监督合法函数调用格式及每种 assistant 轮次实际需要的结束边界，不粗暴为所有动作添加同一个 EOS。12B 的 handover 正文已受监督，模板结束 token 被 mask 是编码缺口，但尚不是循环的已证实原因。

如果完整轨迹超长，优先挑仍覆盖完整因果链的真实短任务。局部阶段可用于“给定当时工作状态后的修复/恢复”训练，但输入只能包含当时可得信息，必须从相应文件快照重新执行；部署入口也要使用同种状态结构。若做了新的阶段入口，先固定它作为两臂共同 Agent，再比较 base/LoRA；不能训练短摘要入口、评测完整历史入口，却把差异全部归因于权重。

**5．训练工程按瓶颈决定，不锁死 FSDP。** 现有 DDP 每卡载入完整冻结基座，31B 加载约占 17.2 GiB，因此 FSDP 分片有现实价值。同时，旧前向 OOM 位于 SDPA，CPU offload 后反向 OOM 的具体算子仍未定位，不能把最后观察到的 layer 53 当作确切故障算子。

首日先做 CPU 分析，再用一次短的手动 GPU 命令复现实际 attention mask、stride、dtype 下的前后向分配，核对现有 [grouped attention 候选](../../research/005/grouped-attention-20261011/results.md)是否值得接入。分析与诊断合计约 30–60 分钟，GPU 诊断不超过约 0.5 配额小时，不加载完整 31B，不另建算子测试项目。若没有明确收益，停止扩展这个分支。

主要容量候选采用 [HF PEFT FSDP-QLoRA](https://huggingface.co/docs/peft/main/accelerate/fsdp)，保留官方 QAT 来源、现有 q/o 与 MLP LoRA 模块、rank 8/alpha 16、梯度检查点和分块 loss。现有 NF4 `uint8` 缓存不能用普通 dtype 转换冒充 FSDP 兼容；需按 [bitsandbytes FSDP 文档](https://huggingface.co/docs/bitsandbytes/main/fsdp_qlora)处理浮点容器中的量化打包、quantization metadata、加载 dtype，以及冻结/可训练参数的分片策略。导出时收集完整 adapter state，不能原样沿用 DDP 的 rank0 保存假设；保存独立 PEFT adapter，不为评分重合并或替换固定 CT 基座。版本以已成功环境和实际兼容结果固定，不在正式运行时追随依赖最新版。

容量判断看三项：train 真实样本能连续完成更新；所选长度覆盖多少有效素材、每小时处理多少独立问题/监督 token；导出的 adapter 能在官方 CT 服务加载，请求确实使用它，并完成实际修复尝试。修复收益另由 A/B 判断。先达到有效数据所需的 4K–8K，不把合成 2K、单次 forward 或 loss 下降当完成。NF4 训练与 CT 推理有数值差异，模板对齐不能消除，因此后续收益必须在 CT 上测。

给容量路线约一个工作日和约 2 个 GPU 配额小时的首轮上限，包含 GPU 诊断、冷启动、分片尝试与导出；CPU 开发时间另计。若仍不能容纳有效样本：写清静态权重、激活、通信/CPU offload 中剩余的瓶颈及所需资源；保留已完成的数据和 Agent 结果。能用真实较短任务，就做小规模任务 SFT；否则单独提出更大显存的成本方案，不能擅自租卡，也不恢复无限长度/平台扫描。

**6．第一份任务 adapter 要尽快形成，但数量服从数据质量。** 筛选 64–128 个问题不应成为必须等齐的条件。若先有 16–32 个独立问题具备完整证据和足够行为覆盖，可先做机制性小实验；它不是泛化已证实的产品模型。64–128 是首轮扩展目标，256–512 要在新开发问题上看到收益后再启动。

起始配方保留 QLoRA r8/alpha16、dropout 0、学习率建议 2e-5、1 epoch，复用现有优化器和梯度累积习惯并写明实际有效 batch。保存一个中间 checkpoint 和最终 adapter；不同时扫 rank、学习率、epoch、多个训练框架。按问题去重及限制重复片段权重，避免一条长轨迹或多个恢复切片主导训练。参数只是初始实验选择，不引用其他模型论文把它们写成最优。

训练侧记录实际输入/监督 token、更新步数、峰值、吞吐、数据与基座身份；评测侧确认请求确实路由到 adapter。若训练拟合改善但 CT 修复退步，先看具体动作与遗漏、模板/模块映射、量化迁移，不直接加 epochs。

**7．Agent 只研究一个有机会救回真实失败的改动。** 完整轨迹路线下，首份权重对照保持当前单 Agent；阶段轨迹路线按第 4、8 项固定两臂共同入口。并行候选优先做“失败反馈驱动的一次纠正”，独立 reviewer 是可选实现，不是必须加上的角色。

触发依据应是可观察的证据：命令本身无效、修改后相同有效检查仍失败、需求分支明确遗漏，或连续相同拒绝。原题、当前 diff、相关源码和执行结果必须传到纠正步骤；换一个角色但不传原题和状态没有价值。只剩很少时间时保存当前候选，不能启动没有机会完成的第二轮。

准备第二次生产修改前保存候选补丁；纠正后用相同的有效命令比较，能证实退步就恢复原候选，最后确认实际工作树与选中补丁一致。基于可见检查选补丁仍可能漏掉隐藏回归，报告其证据范围。不要以 reviewer 自信程度代替执行结果，不把非空 submit 当正确性判据。

原两阶段方案曾让 repair 吃完整个预算而 reviewer 从未进入。当前官方 YAML 没有通用条件分支或每阶段独立硬超时；提示词中的“预留一分钟”只是软约束。若采用 AgentTool，所有调用、保存/恢复与交接都要在官方可提交接口中发生，不能依赖只存在于本地研究 runner 的控制器。[现有接口核查](../../research/012/agent/architecture.md)

训练和 Agent 两条线不互相等待。第一轮不叠加多候选搜索、重型图检索、常驻技能、自建 verifier 或 RL。thinking/output 预算缩减可能减少无效生成，但只在训练对照完成、轨迹表明生成成本确实阻碍修复时，作为下一次单变量实验。

**8．开发对照要能回答“多修了什么，又损失了什么”。** 先冻结 12–16 个新外部开发问题，目标至少四个训练外仓库，覆盖多文件/关联分支、接口约束和错误恢复。按问题元数据与环境可复现性选取，事先固定顺序和替补规则，不按我们模型输赢挑题。排除旧八题、旧诊断题、所有预留题和训练问题的重复快照；同一 repo/fork 家族整体分配，避免近重复泄漏。

优先采用数据源自带判据、项目已有回归测试和官方 harness。CPU 先确认 buggy 状态确实失败、参考修复能通过、被测模块来自当前工作树；能取得相关已有 P2P 就同时运行。只有狭窄 F2P 见证的结果单列为机制证据，不汇报成完整 resolved。不能为了凑题数又选满单行修复、没有回归证据的轻量池。

公开官方开发题可复用已获准的 dev 身份做服务/环境对齐，结果与训练外面板分开报告；不打开保留评测题来“扩大样本”。本项目不新增专用测试文件或套件，必要核对采用一次性 Shell/Python、上游已有测试与官方评测。环境失败记明原因，不用模型生成“通过”标签补齐结果。

| 比较 | 固定项与变化 | 能回答的问题 |
|---|---|---|
| A：31B base + 当前 Agent | 复用冻结 runtime-v2，先在新面板取真实基线 | 新面板是否有区分力，失分集中在哪 |
| B：31B LoRA + 同一 Agent | 与 A 同题、同时间、同服务配置、同采样，只变权重 | 后训练带来的新增修复、回退与运行成本 |
| C：胜出权重 + 一次纠正候选 | 与胜出臂比较完整同一面板，不只跑其失败题 | 纠正能救回什么，是否伤害已成功题 |

若新阶段输入是训练所必需，A/B 都先采用同一个冻结阶段入口，同时用原 runtime-v2 保留系统基线；不能把不同 Agent 的 A/B 称作纯权重消融。若 C 与权重明显存在交互，再补缺失的第四格，不默认做全量四臂消耗。

首次 12–16 题仅作开发筛选。逐题列 W/L、已有回归、超时和失败归因；对会改变选择的胜负成对复跑，保留每次结果而不是挑最好一次。若有正向信号且资源允许，再预先冻结一批新问题，使累计达到约 24–32 题，分开报告筛选集和新增确认集。单题净胜可以做探索性提交，不能宣称稳定提升；全平或全满则说明当前面板/机制没有提供选择证据，停止原样重复。

提交前，用官方 Getting Started 对齐的服务设置观察 LoRA 加载、实际请求路由、KV/并发容量和一组串行任务耗时，特别保留官方建议的 `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1`。训练能加载、低并发本地能加载，都不保证正式配置可运行。[官方 LoRA 讨论](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/749191)、[部署证据归档](../../research/007/official-data-20261017/report.md)

选择规则保持简单：LoRA 有真实净收益且运行可承受，就用 LoRA；LoRA 无收益而 Agent 改动有收益，先用 base 加改进 Agent；两者都无新增修复，就保留 0.15 基线，改最集中的失败来源，不为满足时间表重复提交。正式包冻结模型、adapter、Agent、服务来源和文件指纹，记录 submission ID；等实际 score/error 返回再谈提分。

**9．时间和算力要留给能改变决策的实验。** 下表是下一次执行的建议，不是本轮已经开展的作业，也不把历史账号余额当作当前独占配额。

| 从执行启动起 | 并行工作 | 交接者应拿到的结果 |
|---|---|---|
| 0–6 小时 | 冻结协议；训练素材长度与来源筛选；CPU 准备新开发题；复用最新正式回执 | 当前基线、真实 train 长度分布、明确数据用途、能运行的第一批开发问题 |
| 6–24 小时 | 有上限的容量诊断/分片；素材重放；单一纠正机制开发 | train 真实样本连续更新与导出，或明确容量缺口；新面板 A；完成的数据而非空目录 |
| 24–48 小时 | 第一份任务 SFT；同 Agent 的 A/B；训练不可行时继续 base Agent 对照 | 原始补丁和逐题 W/L，真实 adapter 或真实未执行原因 |
| 48–72 小时 | C 与关键复查；正式服务条件验证；择优冻结 | 有依据的提交候选；若已授权执行且候选值得提交，完成真实提交并取回 ID |
| 随后一周 | 只沿有效数据/机制扩量；追加新问题确认 | 256–512 个独立问题的可用性与成本实数，更广范围修复收益，下一份候选 |

首轮可保留约 **14 个 GPU 配额小时**为计划上限：容量约 2h，采样和训练约 5h，先为修复对照与串行服务确认保留约 6h，约 1h 处理必要恢复。按当前公开 2×倍率，相当于约 7 小时 L4×4 墙钟；这是配额预算，不是 GPU 卡时。**这不保证跑完全部 A/B/C：**12–16 题 × 三臂 × 5 分钟的串行生成上界已是 3–4 小时墙钟、约 6–8 配额小时，尚未计启动、准备和复查。默认先完成 12 题 A/B，依据实际耗时把采样/训练剩余额度转给 C 和关键复查；C 若预算不足就延后，不能只评失败题却宣称整体有收益。研究四并发可降低墙钟，但不能用它省下的估计值承诺正式服务时限。

冷启动、失败和重试都计入；不同时在多个账号重复启动，GPU 由一名负责人统一排程，按会话授权和实时余额执行。扩量费用按首轮真实吞吐估算，不凭总 token 数或论文的 H100 速度承诺。

数据/CPU 负责人交付已重放素材及用途、长度、覆盖；训练负责人交付真实容量和 adapter；Agent/评测负责人交付同预算逐题胜负、关键行为与提交包；主负责人解释下一笔计算会验证什么，并统一提交。评测不足的资金不能被“再训一轮”提前用掉。

执行产物在 `research/015/` 按实际需要归档，复用已有载体和记录结构；现在不创建空结果、blocked/skipped JSON 或新检查体系。每次汇报回答：新增修好哪些问题、退步哪些问题、花了多少实测或明确估算的配额、提交及分数处于什么状态。

**最终接力任务：在同一套可部署的 31B 协议中，把训练素材、实际模型失误和修复反馈接起来；先得到第一份能解释得失的任务 adapter，再把已证明有效的行为扩到更多独立问题。** 目前最值得增加的投资是训练分布贴近实际 Gemma 行为、开发题和判据更有区分力，以及真实失败后的有效纠正；还没有证据支持继续放大旧 34 条配方、堆更多角色，或以某个公开 0.22 当作我们可保证达到的成绩。

## 2026-10-22 执行后的修订

实际证据与配额以 [P015执行记录](../../research/015/README.md) 为准：31B已完成真实6846-token更新、完整LoRA导出与CT请求路由；新四仓开发基线为5/12，正式分数仍0.15。真实成功轨迹约11.8K，普通final reasoning尚不受现有编码器支持，因此把“完整轨迹塞入8K”改为“完整原件留存、按实际请求构造完整因果状态的action RFT”，不手工截历史、不把局部窗口叫整任务SFT。每issue先按正确性/完整响应筛选，再选有生产edit的合规目标。

6次开发超时约99.8%时间等待模型API，而工具只占数秒；API时间含排队和prefill，尚不能断言thinking是唯一根因。权重A/B继续保持4096预算一致，另设在AB全部结束后执行的base/1024预算机制臂，以真实结果决定下一步，不将它与LoRA收益混算。
