## 3. Agent主线：完整修复流程

采用一个共享12B CT服务，不为每个角色加载模型。流程为：

```text
定位(base) → 修复A(base或指定adapter) → 独立验收(base)
  ├─ 证据足够且未见反证 → 恢复/确认A → 最终提交(base)
  └─ 有具体反证且预算足够 → 从同一baseline修复B → 独立验收
                               → 依据证据选择A或B → 恢复选中快照 → 提交
```

### 3.1 编排与上下文

优先用官方支持的YAML AgentTool与已有顺序角色配置组成条件流程。旧one_handoff仅作角色结构参考，其技能名仍含下划线；实际复用single_state中合法的 `working-state/source-edit/source-probe` 技能包，避免重遇已有官方编译拒绝。base协调器负责调用角色与决策；不要把外部研究用Python coordinator当作正式提交入口。正式compiler不支持任意Python root/controller动态导入。

定位、修复、验收使用独立消息上下文；可复用 `output_key` 与 `include_contents: none`，通过文件handle传递真实证据。实际运行时核对角色确实收到原问题与必要代码、没有继承整段错误历史；只追加状态卡不能称为上下文重置。候选生成与验收共享同一任务沙箱，**串行修改工作区**。

验收者先看问题、实际diff与执行证据，不看修复者的自信结论或冗长理由。它检查需求主体是否实现、是否只是增加导入/测试脚本、是否误改接口、已有检查和一次性复现是否运行了修改后的真实源码。移除edit/write工具并不构成硬只读，`run_command`仍可写文件；实际验收不得修改生产源码，记录其前后diff，临时验证产物放临时目录。

### 3.2 双候选与选择

复用快照实现保留baseline、A、B及选定版本。每个候选的patch、源码指纹、命令结果、验收结论绑定同一ID；禁止验收B却提交A的工作树。B从最初baseline恢复，重新依据另一条根因或方案修复；可继承原问题、定位证据及A的反证，不能在A补丁上继续改后冒称独立路线。

现有 `patch_store` 最多四个快照、八文件、单文件200KiB/合计512KiB，包含未跟踪文件；HEAD变化会拒绝恢复。保存/恢复错误按实际失败处理，不静默删文件或放宽保护规则。现有 `working_state` 只有单份state/handoff，需增加按候选和阶段区分的轻量运行记录，避免下一角色覆盖上一候选证据；这不是新测试平台。

B不是固定必跑。A已有充分通过证据时及时结束；A只有空补丁、半完成修改、验证失败或根因存在具体反证时，再判断剩余资源是否够完成B及验收。默认只做A、B两条路线，不扩成无边界搜索。最终选择依据需求覆盖与实际执行证据，不以patch长度、模型自评或非空diff直接判优。
